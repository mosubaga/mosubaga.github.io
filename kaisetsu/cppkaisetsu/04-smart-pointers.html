Smart Pointers

Modern C++ lets objects clean themselves up. This program shows RAII and the three standard smart pointers, unique_ptr, shared_ptr and weak_ptr, and there is not a single delete in main.

What the programmer wants you to learn

Lesson 03 ended with a list of things that can go wrong with new/delete: leaks, double deletes, dangling pointers. Smart pointers solve these by giving every dynamic object a clear owner that deletes it automatically.

Smart pointerOwnershipCreated withThink of it as
std::unique_ptr<T>Exactly one ownerstd::make_unique<T>(...)A house key with no copies
std::shared_ptr<T>Several owners; last one cleans upstd::make_shared<T>(...)A shared flat: the last to leave turns off the lights
std::weak_ptr<T>Not an owner; only observesFrom a shared_ptrKnowing the address, but not holding a key

All three live in <memory>. <utility> provides std::move.

The helper types

Resource: a noisy object

Resource prints a message when it is created (Acquired) and when it is destroyed (Released). By reading the output, you can see exactly when each object dies, even though nobody calls delete. (A struct is a class whose members are public by default.)

name(std::move(label)) moves the string into the member rather than copying it, a small efficiency habit. You will see std::move again in Section 2.

share_resource

The parameter is a shared_ptr taken by value, so calling this function creates one more owner for as long as the function runs. The comment says it is "deliberate", to show the owner count go up.

Node: a parent/child pair

A node owns its child (shared_ptr) but only observes its parent (weak_ptr). Section 4 explains why that asymmetry matters.

Section 1: RAII and scope-based cleanup

The extra pair of braces { ... } creates an inner scope. scoped_resource is a local variable inside it. When execution reaches the closing brace, every local variable in the scope is destroyed. The unique_ptr's destructor then deletes the Resource it owns.

RAII = Resource Acquisition Is Initialization

A long name for a simple idea: tie a resource's lifetime to an object on the stack. When the object is created it takes the resource; when it is destroyed it gives it back. Because C++ destroys local objects at a predictable moment, even when an exception is thrown (lines 39–40), cleanup cannot be forgotten. Java's try-with-resources and Python's with are the closest equivalents, but in C++ it works for every scope automatically.

Syntax note: auto lets the compiler deduce the type; here it is std::unique_ptr<Resource>.

Section 2: unique_ptr, exclusive ownership

Moving ownership

A unique_ptr cannot be copied; line 44 would not compile. If two pointers both owned the object, both would try to delete it. Instead ownership is moved: std::move(original) hands the object to owner and leaves original empty (null).

Arrays

std::make_unique<int[]>(3) creates an array of three ints set to zero. The [] in the type means it will automatically use delete[], so the mismatch problem from Lesson 03 cannot happen. Bounds are still not checked, though. (In practice, std::vector is usually the better choice for arrays.)

A custom deleter

Sometimes "clean up" means something other than delete, such as closing a file or releasing a network connection. A unique_ptr can be given a custom deleter to call instead. Here it is a lambda (an anonymous function, like (r) -> { ... } in Java): it prints a message and then deletes. decltype(deleter) asks the compiler for the lambda's type, because the deleter type is part of the unique_ptr's type.

Borrowing with get() (line 64)

ptr.get() returns a plain raw pointer to the owned object, useful for calling older functions that take T*. That raw pointer is only borrowed: never delete it and never wrap it in a second smart pointer, or the object would be deleted twice.

Notice that exclusive resource is not released here. owner belongs to main's outer scope, so it lives until the very end of the program (look at the last line of the full output).

Section 3: shared_ptr, shared ownership

A shared_ptr keeps a reference count: how many shared_ptrs currently own the object. Copying one adds an owner; destroying or resetting one removes an owner. When the count reaches zero, the object is deleted. use_count() lets you peek at the number.

This is the closest thing in C++ to how Java or Python manage objects: an object lives as long as someone refers to it.

Two warnings from the comments

use_count() is for illustration and debugging; don't base program logic on it. And shared ownership is not shared safety: if two threads modify the Resource at the same time, you still need a lock.

Section 4: weak_ptr and ownership cycles

The problem: cycles

Reference counting has a weakness. If a parent owns its child and the child owns its parent, each keeps the other's count at least 1. When the outside world lets go, neither count reaches zero and both objects leak. (A garbage collector would detect this; reference counting cannot.)

The fix: one direction only observes

Node "parent"child: shared_ptr
owns (shared_ptr)
Node "child"parent: weak_ptr
observes (weak_ptr)

Only the downward edge counts as ownership, so there is no cycle of owners.

Step by step:

  1. Two nodes are created; parent->child owns the child, child->parent only observes the parent.
  2. observer is a weak_ptr declared outside the scope so we can check on the parent later.
  3. observer.expired() is false: the parent still exists.
  4. child->parent.lock() tries to get a temporary shared_ptr. If the parent is alive, it succeeds and we can safely use it inside the if.
  5. At the closing brace, the local parent and child variables are destroyed. The parent's count drops to 0, so it is destroyed; that releases its child member, so the child is destroyed too.
  6. Now observer.expired() is true and lock() returns an empty pointer.
Always lock(), then check

A weak_ptr cannot be dereferenced directly. As lines 103–104 explain, expired() is only a snapshot (the object could disappear right after you check). The safe pattern is if (auto p = weak.lock()) { ... }: you hold a real owner while you use the object.

Syntax note: if (auto x = ...) declares a variable and tests it in one step. A smart pointer counts as true when it is not empty.

Takeaways

  • Default to std::make_unique. Move it with std::move when ownership changes hands.
  • Use std::make_shared when several parts of the program genuinely share an object's lifetime.
  • Use std::weak_ptr for back-references and observers, so cycles cannot leak.
  • Raw pointers from get() are borrowed: never delete them, and keep the owner alive while you use them.
Try it yourself

Change line 26 to std::shared_ptr<Node> parent; and line 93 to if (auto temporary_owner = child->parent) {. Run the program: the Destroyed node messages disappear. That is the leak caused by an ownership cycle.
