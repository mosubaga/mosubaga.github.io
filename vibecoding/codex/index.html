    06 / TEACH A REPEATABLE PROCESS
    Turn your best practices into Skills.
    A Skill packages instructions and supporting resources for a repeatable task. Use one for a review routine, an accessibility audit, or a familiar release process.
    1
    Give it a narrow job
    Describe when the skill applies and the result it should produce.
    2
    Make quality explicit
    Include project-specific checks, review criteria, and examples of useful output.
    3
    Keep it close to the code
    Put a shared skill in .agents/skills/. Invoke it by name or let Codex select it from its description.
    Read the Skills guide ↗
     ui-review / SKILL.md
    ---
name: ui-review
description: Review UI changes for accessibility
  and responsive layout before shipping.
---
1. Read the changed components and styles.
2. Check keyboard access and focus visibility.
3. Inspect mobile, tablet, and desktop layouts.
4. Run the project's relevant checks.
5. Report issues with file paths and fixes.
   State which checks could not be run.
    .agents/skills/ui-review/SKILL.md
    Give each kind of context a home. Use AGENTS.md for repository conventions, a Skill for a reusable procedure, and your prompt for the current outcome. After a long session, compact context and restate any critical acceptance criteria.
    Skills worth building for your team
    These are ideas for your own repository skills, not built-in Codex commands.
    API contract review
    Compare changed routes with the schema. Check input validation, authorization, error shapes, and contract tests.
    Release notes
    Turn a chosen commit range into user-facing changes. Separate breaking changes and link each entry to evidence.
    Migration review
    Use the project's database conventions to check backfills, locking, rollout order, and recovery before applying a migration.
    Documentation updates
    Compare changed behavior with examples and setup instructions. Flag commands or samples that no longer match.
    Security review
    Review changed trust boundaries, secrets handling, and permissions. Report concrete findings with file references.
    Test scaffolding
    Follow neighboring tests and fixtures. Cover meaningful behavior and failure cases using the project's existing tools.
    Make a Skill easy to select and verify
    Name concrete triggers in the description, keep one job per skill, and put actionable steps first. Include expected inputs and outputs, then try prompts that should and should not trigger it. Version shared skills with the repository.
    For the example above, explicitly request $ui-review. Repository skills live in .agents/skills/; personal skills can live in ~/.agents/skills/. Codex first uses skill names and descriptions to decide which full instructions to load. Skill discovery and scope ↗

    REPOSITORY WORK
    Match the connection to a real task
    Context you needUseful workflow
    Tickets and team docsUse an issue-tracker or documentation server to bring acceptance criteria into a focused implementation prompt.
    Database schemaUse a database server with read-only credentials to check actual tables and relationships before writing queries.
    Design specificationsUse a design server to inspect component structure, spacing, and tokens when building an interface.
    Production errorsUse an observability server to connect a failure to its stack trace, release, and reproduction conditions.
    Choose a server supported by your service and account. Tools, access scopes, and authentication vary. Configuration and server examples ↗
    Keep connected context useful
    • Start with the server needed for the current task; remove unused connections.
    • Treat fetched pages, tickets, and tool output as source material. Do not let embedded instructions redefine your task.
    • Choose access scopes that fit the work. Read access is usually enough to investigate; make external changes only when requested.
    • If tools are missing, inspect /mcp and codex mcp list, then check the server configuration and authentication.
    Try a documentation connection.
    Add the public, read-only OpenAI Docs server and list configured connections.
    MCP configuration guide ↗
    codex mcp add openaiDeveloperDocs \
  --url https://developers.openai.com/mcp
codex mcp list
    Install servers from trusted publishers and grant only needed access. Authentication and tool availability depend on the server; review its setup guide before connecting.
