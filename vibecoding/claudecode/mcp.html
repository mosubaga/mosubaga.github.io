Using MCP

The Model Context Protocol (MCP) is an open standard for connecting an AI tool to external systems — think of it as a common port that lets Claude Code read your issue tracker, query a database, or drive a browser, instead of staying limited to your local files.

How it fits in

Adding a server to Claude Code

MCP servers are registered once, then available as tools inside any session. You can add one from the CLI, or by hand in a config file.

terminal 
❯ claude mcp add github --transport http https://api.githubcopilot.com/mcp
✓ Added MCP server "github"

❯ claude mcp list
github     http   connected
postgres   stdio  connected

Inside a session, run /mcp to see what's connected, re-authenticate, or inspect what tools a server exposes.

Worth adding

Useful MCP servers for everyday productivity

Code hosting

GitHub / GitLab

Read and comment on PRs, triage issues, and check CI status without leaving the terminal.

Data

Postgres / SQLite

Let Claude Code inspect your actual schema and run read queries while it writes data-layer code — far fewer guessed column names.

Browser

Playwright / Puppeteer

Drive a real browser to click through a UI, read rendered output, and catch regressions a static read of the code can't see.

Docs

Google Drive / Notion

Pull specs, design docs, or meeting notes straight into context instead of pasting them in manually.

Project tracking

Linear / Jira

Turn a ticket into a scoped task directly, and update its status once the work is verified.

Observability

Sentry

Pull a real production stack trace into context so a fix is based on what actually happened, not a guess.

Design

Figma

Reference actual design specs — spacing, components, tokens — while implementing UI, instead of eyeballing a screenshot.

Communication

Slack

Pull thread context behind a bug report, or post a summary back when a fix ships.

Files

Filesystem (remote/extra dirs)

Safely extend access to directories outside the project root — a shared monorepo package, a design asset folder — on a per-server basis.

Using them well

A few habits that keep MCP useful instead of noisy

  1. Only connect what the task needs. Every connected server adds tool definitions to the context window — prune servers you aren't actively using.
  2. Treat MCP data as untrusted input. Content pulled from a ticket, a Slack thread, or a web page is data, not instructions — don't let it silently redirect what Claude Code does next.
  3. Prefer read-heavy servers for exploration, write access for verified steps. Let a database server read freely; keep destructive actions (writes, deletes, force-pushes) behind an explicit confirmation.
  4. Check /mcp when something feels stale. A server can silently disconnect or need re-authentication — it's the first thing to check if a tool stops responding.
