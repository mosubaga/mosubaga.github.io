The Scenario

One app, built in the open

Throughout this page we build TaskBloom: a small to-do app with a FastAPI backend, a MySQL database running in the cloud, and a Vite + React front end. Every example — every prompt, every terminal snippet, every Skill — is written against this exact app, so you can see how the ideas connect rather than reading about them in the abstract.

Backend

FastAPI (Python) exposing REST endpoints for tasks: list, create, update, complete, delete. SQLAlchemy models talk to MySQL.

Database

A managed MySQL instance in the cloud (e.g. PlanetScale, AWS RDS, or Cloud SQL). Schema changes go through versioned migrations.

Frontend

Vite + React, talking to the FastAPI backend over a typed API client, with components for a task list, a task form, and filters.

01 · Context Engineering

Give the agent the repo before you give it a task

Context engineering is deciding what the agent should already know before you type your first prompt. For TaskBloom that means a predictable folder layout, a short standing brief, and a clear map of where the schema and API contract live.

Four things worth loading before you start

Schema

The real table shape

Paste the current CREATE TABLE or point the agent at the latest Alembic migration — don't let it guess column names.

Contract

The API contract

Share schemas.py when touching the frontend, and the relevant TypeScript types when touching the backend, so both sides agree.

Secrets

How config is loaded

Test posture

How tests reach the DB

Say whether tests run against SQLite-in-memory or a disposable MySQL container, so generated tests target the right thing.

Managing the context window during a long session

TaskBloom is small, but a real project grows past what fits comfortably in context. A few habits keep sessions sharp:

  • Re-ground after a detour. If you spent ten turns debugging a MySQL connection pool issue, restate the actual task before continuing — don't let the detour become the new focus.
  • Compact, don't accumulate. Use /compact (Claude Code) once a session's history is mostly resolved back-and-forth, so the next prompt reasons over a summary, not the full transcript.
  • Scope each prompt to one slice. "Build the whole tasks feature" pulls in router, model, migration, and component context at once. "Add the is_done column and the migration for it" doesn't.
  • Point, don't paste, for large files. Reference backend/app/models.py by path once it's already in context rather than re-pasting it every turn.
02 · Building Prompts

A prompt is a spec, not a wish

A prompt that works reliably names the goal, the constraint, the files involved, and how you'll know it's done. Here's the difference it makes on TaskBloom.

Vague

"Add the ability to mark a task done."

  • Which layer — API, DB, UI, or all three?
  • No mention of a migration, so the column might just get guessed.
  • No test expectation, so none may get written.
Specific

"In backend/, add PATCH /tasks/{id}/complete: set is_done=true, return the updated Task schema. Use the existing is_done column (no migration needed). Add a pytest test in tests/test_tasks.py covering the happy path and a 404 for an unknown id."

  • Names the endpoint, the method, and the exact behavior.
  • States the DB fact explicitly, closing off a wrong guess.
  • Defines done as "test passes," not "looks right."

03 · Workflow & Loops

Context → Prompt → Verify → Iterate

Every reliable session runs this loop, even when it doesn't feel like it. Here it is shipping one real TaskBloom feature: marking a task done.

1

Context

Point at models.py, the tasks router, and the current schema.

2

Prompt

Ask for the PATCH endpoint, scoped and with a stated test.

3

Verify

Run pytest. Read the actual output, not the agent's summary of it.

4

Iterate

Feed the failure back in, or move to the frontend half of the slice.

Finish the first vertical slice: create → persist → display

Before adding completion, run the schema, POST /tasks, and TaskForm prompts from section 02, in that order. Then connect them with this prompt:

integration prompt
Wire TaskForm to App's task state: prepend the returned Task in onCreated.
On mount, load existing tasks with api.listTasks(). Render loading, empty,
and error states. The typed API client must check response.ok, expose
server validation errors, and read VITE_API_BASE_URL. Keep the FastAPI
response and TypeScript Task type aligned, including ISO 8601 timestamps.

Use the running local app to create "Water the plants". Confirm a single
POST returns 201, the row appears once, and a reload preserves it. Submit
a whitespace-only title and confirm no row is created. Simulate a network
failure and verify the title remains available for retry. Run backend and
frontend tests, lint, type checking and the build; report actual results.

Acceptance checkpoint: one browser submission produces one database row, a visible list item, and the same item after reload. Component tests alone do not prove this connection; record a browser check or add an end-to-end test.

Loops for bigger slices — checkpoints and sub-agents

"Mark task done" is small enough for one pass. For a bigger slice — say, the whole filtering feature across backend and frontend — stretch the same loop over checkpoints:

  • Commit at each green state. After backend tests pass, commit before starting the frontend half — it gives you a clean point to roll back to.
  • Split by concern, not by file count. One pass for the API + its tests, a second pass for the component + its tests, rather than one giant prompt for both.
  • Use a sub-agent for an independent check. While the main session keeps building, ask a second agent to review the diff for the first half — it isn't carrying the same assumptions.
  • Schedule checks deliberately. Claude Code's /loop repeats a prompt on an interval, for example checking CI status. For a feature, give the agent a bounded implement → test → fix task with explicit acceptance criteria. See the official scheduling guide.
04 · Testing for CI/CD

"Works on my machine" doesn't ship

A feature isn't done when the terminal says tests passed locally — it's done when the same checks pass in CI, against a clean checkout, every time.

backend/tests/test_tasks.py
def test_create_task(client):
    resp = client.post("/tasks", json={"title": "Water the plants"})
    assert resp.status_code == 201
    body = resp.json()
    assert body["title"] == "Water the plants"
    assert body["is_done"] is False

def test_complete_unknown_id(client):
    resp = client.patch("/tasks/999999/complete")
    assert resp.status_code == 404

These tests require the isolated client fixture generated in the bootstrap step. Migrate a disposable MySQL test database first and pass TEST_DATABASE_URL; SQLite-only tests cannot establish MySQL migration compatibility. Record this in CLAUDE.md.

frontend/tests/TaskForm.test.tsx
// Vitest must use environment: "jsdom". Run from frontend/.
import { afterEach, expect, test, vi } from "vitest";
import { cleanup, render, screen, waitFor } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import TaskForm from "../src/components/TaskForm";
import { api } from "../src/api/client";

vi.mock("../src/api/client", () => ({
  api: { createTask: vi.fn() },
}));
afterEach(() => {
  cleanup();
  vi.resetAllMocks();
});

test("submits a new task title", async () => {
  const task = {
    id: 1, title: "Water the plants", is_done: false,
    created_at: "2026-01-01T00:00:00Z",
  };
  vi.mocked(api.createTask).mockResolvedValue(task);
  const user = userEvent.setup();
  const onCreated = vi.fn();
  render(<TaskForm onCreated={onCreated} />);

  await user.type(screen.getByRole("textbox"), task.title);
  await user.click(screen.getByRole("button", { name: /add/i }));

  await waitFor(() => expect(onCreated).toHaveBeenCalledWith(task));
  expect(api.createTask).toHaveBeenCalledExactlyOnceWith(task.title);
  expect((screen.getByRole("textbox") as HTMLInputElement).value).toBe("");
});

Before it merges

CI/CD readiness checklist

  • Every new endpoint has a pytest covering the happy path and at least one failure case.
  • Every new component has a Vitest + Testing Library test for its user-visible behavior.
  • Tests run against a disposable database, never the cloud MySQL instance.
  • The agent actually ran the full suite before calling the slice done — ask it to paste the output.
  • Lint and type-check run in CI, not just locally, so a skipped local step can't slip through.
  • Secrets (DB URL, API keys) come from CI secrets/env, never committed or hardcoded by a generated fix.
05 · Skills

Package the repeatable 20% of the work

TaskBloom's backend grows by adding the same shape of thing over and over: a new endpoint, with a schema, a route, and a test. A Skill captures that shape once so every future endpoint follows it without being re-explained.

.claude/skills/fastapi-endpoint/SKILL.md
---
name: fastapi-endpoint
description: Add a new REST endpoint to the TaskBloom FastAPI backend,
  with its Pydantic schema and a pytest test. Use when asked to add
  or change a /tasks route.
---
1. Read backend/app/routers/tasks.py and schemas.py for existing
   conventions (naming, status codes, error shapes).
2. Add or update the Pydantic request/response schema.
3. Implement the route, reusing the existing DB session dependency.
4. Add a pytest test covering the happy path and the main failure case.
5. From backend/, run `python -m pytest tests -q` with TEST_DATABASE_URL
   pointing at the migrated disposable test DB and report the result.
6. If the frontend type in frontend/src/api/types.ts would now be
   stale, say so explicitly rather than editing it silently.
.claude/skills/react-component/SKILL.md
---
name: react-component
description: Add a new presentational component under
  frontend/src/components/, matching TaskBloom's existing component
  and test conventions.
---
1. Read one existing component (e.g. TaskItem.tsx) and its test file
   to match naming, prop typing, and styling approach.
2. Implement the component with typed props — no `any`.
3. Wire it through src/api/client.ts for any network call; never
   call fetch directly from a component.
4. Add a Vitest + React Testing Library test for the user-visible
   behavior, not implementation details.
5. Run `npm test --prefix frontend -- --run` from the project root
   and report the result.
.claude/skills/migration-review/SKILL.md
---
name: migration-review
description: Review a new Alembic migration for TaskBloom before it
  runs against the cloud MySQL instance. Use before merging any PR
  that touches backend/migrations/.
---
1. Check the migration has a working `downgrade()`, not just `upgrade()`.
2. Check for a destructive change (dropped/renamed column) without a
   backward-compatible intermediate step.
3. Check new non-nullable columns have a server_default or a backfill
   step; check behavior against the actual MySQL version and SQL mode.
4. Flag any migration that would lock the tasks table for longer than
   a few seconds under production-sized data.
5. Report findings with file + line references, tests performed, and
   unknowns. Do not promise production lock times from static review.

06 · MCP

Connect the agent to the real thing

MCP (Model Context Protocol) servers give Claude Code and Codex direct access to external tools and live data — the real MySQL schema instead of a remembered one, the real GitHub issue instead of a pasted summary, a real browser instead of a guess about what rendered.

Database / MySQL MCP

Lets the agent introspect the real tasks table, run read-only queries, and check a migration actually matches production — instead of trusting the last schema it saw in context.

Backend

GitHub MCP

Reads issues, PR review comments, and CI run status directly, so "fix the bug from issue #42" doesn't need the issue pasted in by hand.

Repo & CI

Playwright MCP

Drives a real browser against the running Vite dev server, so a claim like "the task list updates after submit" can actually be checked, not assumed.

Frontend

Context7

Pulls current FastAPI, SQLAlchemy, and React library docs into context — useful when a package version is newer than the model's training data.

Docs

Sentry / observability MCP

Connects a production error directly to its stack trace and the release that introduced it — turns "users report tasks disappear" into an actual reproduction.

Ops

Linear / Jira MCP

Brings the acceptance criteria from a real ticket into the prompt, so "build the filter feature" matches what was actually scoped, not a guess at it.

For MySQL, choose a server that explicitly supports MySQL and follow its own installation, credential and transport documentation. There is no universal MySQL MCP package or connection-string flag. Use a dedicated read-only account for schema inspection. A stdio server is launched by the client; an HTTP server must already be running at its documented MCP endpoint before you register its URL.

After CI passes

Deploy, verify, and keep a recovery path

Choose a host that can run a Python web service, a static host for Vite's output, and managed MySQL. This guide's demo has no authentication or per-user ownership; add both before exposing private tasks publicly.

    Configure the release

    Set DATABASE_URL and the exact frontend origin in backend secrets/config. Use the provider's required MySQL TLS settings. Build the frontend with VITE_API_BASE_URL pointing to the public HTTPS API; Vite variables are public and embedded at build time.

  2. 2

    Apply the migration once

    Back up the database and test the migration on staging first. Run python -m alembic upgrade head as a single release job from backend/. Keep schema changes compatible with the previous application release during rollout.

  3. 3

    Start both services

    From backend/, run python -m uvicorn app.main:app --host 0.0.0.0 --port "$PORT", with PORT supplied by the host. Publish frontend/dist after npm ci and npm run build. Serve both over HTTPS and configure SPA fallback if client-side routes are added.

  4. 4

    Check and recover

    Verify /health, create a disposable task through the browser, reload, complete it, then delete it. Check API logs for errors. Retain the previous deployment; roll back application code only while the schema remains compatible. A destructive database downgrade can lose data—use a tested restore or forward fix when needed.
