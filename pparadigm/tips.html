A USEFUL STARTING POINT

State in objects.
Calculations in functions.

Let an object manage something that changes over time. Let small functions calculate results from inputs. This is a helpful starting point, not a rule: choose the simplest structure that makes your program clear.

PYTHON / PUT IT INTO PRACTICE

Python

Start small; reach for a class when state belongs together.

Run it: Python 3: save as main.py and run python3 main.py.

OOP: keep related state and behavior together

Use a class for something that changes over time, like a study session. Use a plain function when you only need a calculation. An underscore marks an internal attribute by convention; it does not block access.

Python
class StudySession:
    def __init__(self, subject):
        self.subject = subject
        self._minutes = 0

    def study(self, minutes):
        if minutes <= 0:
            raise ValueError("Minutes must be positive")
        self._minutes += minutes

    @property
    def minutes(self):
        return self._minutes

session = StudySession("Math")
session.study(25)
print(session.minutes)  # 25

FP: transform a collection without changing it

List comprehensions are an approachable alternative to map and filter. Keep the calculation independent of input(), printing, files, and network calls so it is easy to test.

Python
def passing_scores(scores):
    return [score for score in scores if score >= 60]

def average(scores):
    return sum(scores) / len(scores) if scores else 0

scores = [45, 70, 95]
passed = passing_scores(scores)
print(passed)          # [70, 95]
print(average(passed)) # 82.5
print(scores)         # [45, 70, 95] — unchanged

Build this habit

Use a dataclass when you mostly need a record of data. Prefer composition to a large inheritance tree: a Player can have an Inventory instead of inheriting from it.

Watch out for this

Avoid mutable default arguments such as items=[]; use None and create the list inside the function. For large collections, consider generator expressions to avoid temporary lists.

JAVA / PUT IT INTO PRACTICE

Java

Use classes for rules and identity; use streams for data transformations.

Run it: JDK 17+: save one example at a time as Main.java; run javac Main.java, then java Main.

OOP: protect a useful invariant

Make fields private and offer a small set of operations that keep the object valid. This counter cannot accidentally become negative through its public methods.

Java
public class Main {
    static final class StudySession {
        private int minutes;

        void study(int amount) {
            if (amount <= 0) {
                throw new IllegalArgumentException("Minutes must be positive");
            }
            minutes += amount;
        }

        int minutes() { return minutes; }
    }

    public static void main(String[] args) {
        StudySession session = new StudySession();
        session.study(25);
        System.out.println(session.minutes()); // 25
    }
}

FP: describe a pipeline with streams

Filter first, then calculate. Keep stream callbacks free of changes to outside variables. A stream is consumed by its terminal operation; create a new stream when you need another pass.

Java
import java.util.List;

public class Main {
    static double passingAverage(List<Integer> scores) {
        return scores.stream()
            .filter(score -> score >= 60)
            .mapToInt(Integer::intValue)
            .average()
            .orElse(0.0);
    }

    public static void main(String[] args) {
        var scores = List.of(45, 70, 95);
        System.out.println(passingAverage(scores)); // 82.5
        System.out.println(scores); // [45, 70, 95]
    }
}

Build this habit

Use an interface when callers need a behavior that could have different implementations. Avoid creating an interface for every class just in case. Records are useful for compact data carriers, but their referenced objects can still be mutable.

Watch out for this

final prevents reassignment of a variable; it does not freeze the object. List.of creates an unmodifiable list, but mutable objects inside it can still change. Use a simple loop when a stream would make the code harder to read.

JAVASCRIPT / PUT IT INTO PRACTICE

JavaScript

Model lasting state with objects; keep array transformations predictable.

Run it: Modern Node.js 18+: save as main.js and run node main.js, or use your browser console.

OOP: give changing state a clear owner

A class is useful when several operations manage the same state. Private fields use #. Keep DOM updates outside the class so you can test the logic without a browser.

JavaScript
class StudySession {
  #minutes = 0;

  study(amount) {
    if (!Number.isFinite(amount) || amount <= 0) {
      throw new Error("Minutes must be positive");
    }
    this.#minutes += amount;
  }

  get minutes() { return this.#minutes; }
}

const session = new StudySession();
session.study(25);
console.log(session.minutes); // 25

FP: use filter and reduce for clear transformations

filter creates a new array. reduce combines values into a result. Give functions descriptive names and handle empty input explicitly.

JavaScript
const passingScores = scores => scores.filter(score => score >= 60);
const average = scores => scores.length === 0
  ? 0
  : scores.reduce((total, score) => total + score, 0) / scores.length;

const scores = [45, 70, 95];
const passed = passingScores(scores);
console.log(passed);          // [70, 95]
console.log(average(passed)); // 82.5
console.log(scores);          // [45, 70, 95] — unchanged

Build this habit

Object literals and factory functions are fine for small features; you do not need a class for every object. If a method depends on this, avoid passing it as a detached callback; wrap the call in an arrow function or bind it.

Watch out for this

const does not make an array immutable. sort() and reverse() mutate their arrays: copy first, for example [...scores].sort((a, b) => a - b). Spreading an array or object only makes a shallow copy.

C++ / PUT IT INTO PRACTICE

C++

Make ownership clear, and use small functions without unnecessary copying.

Run it: C++17: save one example at a time as main.cpp; run c++ -std=c++17 main.cpp -o example, then ./example (Windows: example.exe).

OOP: let the class enforce its rules

A class can keep state private and check each update. const on the accessor promises that it will not modify the object’s ordinary state. Keep objects as local values when you can.

C++
#include <iostream>
#include <stdexcept>

class StudySession {
    int minutes_ = 0;
public:
    void study(int amount) {
        if (amount <= 0) {
            throw std::invalid_argument("Minutes must be positive");
        }
        minutes_ += amount;
    }

    int minutes() const { return minutes_; }
};

int main() {
    StudySession session;
    session.study(25);
    std::cout << session.minutes() << "\n"; // 25
}

FP: pass read-only data into a calculation

Use const references to avoid copying a collection just to read it. A function can use local variables and a loop while still being pure: callers only observe the result, and the input stays unchanged.

C++
#include <iostream>
#include <vector>

 double passingAverage(const std::vector<int>& scores) {
    int total = 0;
    int count = 0;
    for (int score : scores) {
        if (score >= 60) {
            total += score;
            ++count;
        }
    }
    return count == 0 ? 0.0 : static_cast<double>(total) / count;
}

int main() {
    const std::vector<int> scores{45, 70, 95};
    std::cout << passingAverage(scores) << "\n"; // 82.5
}

Build this habit

Prefer standard containers and RAII: resources are released automatically when their owning objects leave scope. Avoid manual new/delete in beginner projects. Use std::unique_ptr when dynamic ownership is actually needed.

Watch out for this

Algorithms and lambdas can make transformations clear, but do not force every loop into an algorithm. Avoid reference captures in callbacks that outlive their referenced variables. Deep recursion can exhaust the stack.

LEVEL UP YOUR CODE

Software engineering principles.

These ideas apply no matter which paradigm you use. They help you write code that is easier to read, test, and change.

Single Responsibility

Each class or function should do one thing well. If you can describe what it does using "and," consider splitting it.

Bad vs Good
# Too many jobs
class UserManager:
    def authenticate(self): ...
    def send_email(self): ...
    def generate_report(self): ...

# One job each
class Authenticator:
    def authenticate(self): ...

class Mailer:
    def send_email(self): ...

Open/Closed Principle

Open for extension, closed for modification. Add new behavior by writing new code, not by editing existing, tested code.

Example
# Add new shapes without touching area()
class Circle:
    def __init__(self, r): self.r = r
    def area(self): return 3.14 * self.r ** 2

class Square:
    def __init__(self, s): self.s = s
    def area(self): return self.s ** 2

def total_area(shapes):
    return sum(s.area() for s in shapes)

DRY — Don't Repeat Yourself

If you find yourself copying and pasting code, extract it into a function or a shared module. But don't over-abstract too early — wait until you see the same pattern three times.

Write Testable Code

Separate logic from I/O. Functions that take inputs and return outputs are easy to test. Functions that read files, hit APIs, or print to the console are harder. Push side effects to the edges of your program.

Composition over Inheritance

Prefer combining simple objects over building deep inheritance trees. A Player can have an Inventory instead of inheriting from it. This keeps your code flexible.

Python
class Inventory:
    def __init__(self):
        self.items = []
    def add(self, item):
        self.items.append(item)

class Player:
    def __init__(self, name):
        self.name = name
        self.inventory = Inventory()

p = Player("Kai")
p.inventory.add("sword")

Debugging Mindset

Read the error message carefully — it usually tells you the file and line. Reproduce the bug with the smallest possible input. Add one print or console.log at a time. Check your assumptions: what do you think the variable contains vs. what it actually contains?

QUICK REFERENCE

Common patterns cheat sheet.

Patterns you'll see in real codebases. Bookmark this section.

Factory

A function that creates and returns objects. The caller doesn't need to know which class is being used.

JavaScript
function createUser(role) {
  if (role === "admin") return new Admin();
  if (role === "guest") return new Guest();
  return new Member();
}

Builder

Build complex objects step by step. Each method returns this so calls can be chained.

JavaScript
class QueryBuilder {
  #parts = { table: "", conditions: [] };
  from(table) { this.#parts.table = table; return this; }
  where(cond) { this.#parts.conditions.push(cond); return this; }
  build() {
    const w = this.#parts.conditions.join(" AND ");
    return `SELECT * FROM ${this.#parts.table} WHERE ${w}`;
  }
}
const sql = new QueryBuilder()
  .from("users").where("age > 18").where("active = true")
  .build();

Iterator

Process items one at a time without loading everything into memory. Great for large data sets.

Python
def fibonacci():
    a, b = 0, 1
    while True:
        yield a
        a, b = b, a + b

for i, num in enumerate(fibonacci()):
    if i >= 8: break
    print(num, end=" ")
# 0 1 1 2 3 5 8 13

Guard Clauses

Handle edge cases at the top of a function and return early. This keeps the main logic un-nested and easy to follow.

JavaScript
function processOrder(order) {
  if (!order) return { error: "no order" };
  if (order.items.length === 0) return { error: "empty" };
  if (!order.paid) return { error: "unpaid" };

  // Main logic — clean and flat
  return { status: "shipped", id: order.id };
}
A SMALL PROJECT TO TRY

Build a study-session tracker.

  1. Start with the data. A session needs a subject and a duration. Write down valid inputs before coding.
  2. Add one object. Use a StudySession to manage elapsed minutes and reject invalid updates.
  3. Extract one calculation. Write a pure function that totals the minutes from a collection of durations. Keep printing and saving outside it.
  4. Combine both ideas. Read the durations from your session objects, pass them to your total function, then display the result.
  5. Check the edges. Try no sessions, one session, and an invalid negative duration. Decide what should happen in each case.

Quick self-check: Can you test your calculation without opening a file, making a network request, or clicking a button? If yes, you’ve created a useful boundary.

Refactor when a real problem appears. You can learn more from one clear working feature than from a huge class hierarchy you haven’t used yet.
