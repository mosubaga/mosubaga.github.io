JSON & Text Handling in Rust

Turning JSON into typed structs with serde, matching patterns in linear time with the regex crate, and the string methods that make most regexes unnecessary.

On this page

serde — add two derives to a struct and JSON parsing and generation come for free.
Strings — String vs &str, UTF-8, and the method vocabulary.
regex — captures, replacement, and a guarantee no backtracking engine can make.
A worked example that parses a log file with regex and emits JSON.

JSON with Serde

Rust has no JSON support in its standard library, and once again that turns out well. The ecosystem converged on serde — a serialisation framework — plus serde_json, one of its many format backends. The split matters: the work you do to describe your data is not JSON-specific, so the same struct also reads TOML, CBOR, MessagePack or CSV by swapping one crate. 

[dependencies]
serde      = { version = "1", features = ["derive"] }
serde_json = "1"
The derive feature is not optional in practice

Without features = ["derive"] you get the traits but not the #[derive(Serialize, Deserialize)] macros, and every example below fails to compile with a confusing "cannot find derive macro" error. It is the single most common serde setup mistake.

Describe the shape once, get both directions

Serialize turns your type into JSON; Deserialize builds it back. The derive macros generate code at compile time, so there is no reflection and no runtime cost for the convenience. 

use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
struct Package {
    name: String,
    version: String,

    // Absent in the JSON? Use the type's Default — here, an empty Vec.
    #[serde(default)]
    keywords: Vec<String>,

    // Option fields are optional automatically: a missing key, or an
    // explicit JSON null, both become None. No #[serde(default)] needed.
    description: Option<String>,
}

fn main() -> Result<(), serde_json::Error> {
    // r#"..."# is a raw string: no escaping of the inner quotes.
    let data = r#"{
        "name": "serde_json",
        "version": "1.0.151",
        "keywords": ["json", "serde"]
    }"#;

    let pkg: Package = serde_json::from_str(data)?;

    println!("{} v{}", pkg.name, pkg.version);
    println!("{:?}", pkg.description); // None — the key was absent

    // And back out again.
    println!("{}", serde_json::to_string(&pkg)?);        // compact
    println!("{}", serde_json::to_string_pretty(&pkg)?); // indented

    Ok(())
}
Function Input / output Use for
from_str &str → T The usual case, and the fastest.
from_slice &[u8] → T Bytes straight from a socket or file, with no UTF-8 check of your own.
from_reader impl Read → T Streams whose length you do not know. See the warning below.
to_string / to_vec &T → String / Vec<u8> Compact output for the wire.
to_string_pretty &T → String Config files and anything a human will read.
to_writer &T → impl Write Writing straight to a file or response body.
from_reader is usually the slow option

This surprises people, and serde_json's own documentation says so plainly: from_reader "is usually slower than reading a file completely into memory and then applying from_str or from_slice on it." It also does not buffer, so passing a bare File means one syscall per few bytes — wrap it in a BufReader at minimum. For anything that fits in memory, read it first and use from_str.

When you do not know the shape: Value

serde_json::Value is an enum covering everything JSON can express — Null, Bool, Number, String, Array and Object. Use it to explore an unfamiliar API, to pass data through untouched, or to handle genuinely dynamic documents. 

use serde_json::{json, Value};

let raw = r#"{"server": {"host": "localhost", "port": 8080}, "debug": true}"#;
let mut config: Value = serde_json::from_str(raw)?;

// Indexing never panics on read: a missing key yields Value::Null,
// so you can walk deep paths without a chain of checks.
println!("{}", config["server"]["port"]);    // 8080
println!("{}", config["nope"]["deeper"]);    // null

// Typed accessors return Option, so a wrong type is your decision,
// not a panic.
let port = config["server"]["port"].as_u64().unwrap_or(8080);
let host = config["server"]["host"].as_str().unwrap_or("127.0.0.1");
let debug = config["debug"].as_bool().unwrap_or(false);

// Writing through an index works, but panics if the parent is not an
// object or array — check with .is_object() when unsure.
config["server"]["port"] = json!(9090);

// json! builds a Value with ordinary JSON syntax, and interpolates
// any Rust expression that implements Serialize.
let payload = json!({
    "user":   { "id": 42, "name": host },
    "active": true,
    "scores": [1, 2, 3],
    "meta":   Value::Null,
});

// Iterate an object when you really do not know the keys.
if let Some(map) = config.as_object() {
    for (key, value) in map {
        println!("{key} = {value}");
    }
}
Use it as a scout, not a destination

Value is the right tool for exploring and for pass-through. It is the wrong tool for the core of an application: every access becomes an Option you have to handle, and you lose the compile-time checking that made the typed version worth it. Explore with Value, then write the struct.

You can also mix the two — #[serde(flatten)] extra: HashMap<String, Value> on a typed struct captures every key you did not name, which is handy for APIs that add fields over time.

Bending the mapping with attributes

Real APIs rarely match Rust naming conventions. Serde's attributes bridge the gap without writing any conversion code by hand. 

use serde::{Deserialize, Serialize};

#[derive(Serialize, Deserialize)]
// Every field is camelCase on the wire, snake_case in Rust.
#[serde(rename_all = "camelCase")]
struct User {
    user_id: u64,             // <-> "userId"
    display_name: String,     // <-> "displayName"

    // One field named differently from the rule.
    #[serde(rename = "e-mail")]
    email: String,

    // Accept an old key too, when reading. Serialising still uses
    // the primary name.
    #[serde(alias = "handle")]
    username: String,

    // Leave the key out of the output entirely when it is None,
    // instead of emitting "bio": null.
    #[serde(skip_serializing_if = "Option::is_none")]
    bio: Option<String>,

    // Never appears in JSON in either direction.
    #[serde(skip)]
    cached_avatar: Option<Vec<u8>>,

    // Missing key -> call this function instead of failing.
    #[serde(default = "default_role")]
    role: String,
}

fn default_role() -> String {
    "member".to_string()
}
Attribute What it does
#[serde(rename_all = "…")] Applies a naming convention to every field: camelCase, PascalCase, kebab-case, SCREAMING_SNAKE_CASE and others.
#[serde(rename = "…")] Renames one field or variant.
#[serde(alias = "…")] Extra accepted name when reading. Repeatable.
#[serde(default)] Missing key uses Default::default(), or a named function.
#[serde(skip)] Field is ignored in both directions; needs a Default.
#[serde(skip_serializing_if = "…")] Omit the key from output when the predicate is true.
#[serde(flatten)] Inline a nested struct's fields, or collect unknown keys into a map.
#[serde(deny_unknown_fields)] Error on any key you did not declare — see the warning below.
#[serde(with = "module")] Custom conversion for one field, e.g. a date format.
Unknown keys are ignored by default

If the JSON has fields your struct never mentions, serde silently drops them. That is usually what you want for an API that keeps growing — but it also means a typo in a config file ("prot": 8080) is silently ignored rather than reported. For config you control, add #[serde(deny_unknown_fields)] and turn that silence into an error.

Enums, and the four ways to put one in JSON

JSON has no notion of a tagged union, so serde offers four encodings. Picking the one that matches the API you are talking to is often the whole job. 

use serde::{Deserialize, Serialize};

#[derive(Serialize, Deserialize)]
enum Event {
    Click { x: i32, y: i32 },
    KeyPress(char),
    Close,
}
Representation Attribute Click { x: 3, y: 9 } becomes
Externally tagged (default) — none — {"Click": {"x": 3, "y": 9}}
Internally tagged #[serde(tag = "type")] {"type": "Click", "x": 3, "y": 9}
Adjacently tagged #[serde(tag = "t", content = "c")] {"t": "Click", "c": {"x": 3, "y": 9}}
Untagged #[serde(untagged)] {"x": 3, "y": 9}

Internally tagged is what most web APIs use — a "type" or "kind" discriminator sitting alongside the data. It cannot represent newtype variants holding a non-object, so KeyPress(char) above would need the adjacent or external form.

untagged costs you your error messages

An untagged enum is tried one variant at a time until one fits. When none does, serde can only report "data did not match any variant" — it cannot tell you which variant nearly matched or why, because it has no way to know which one you intended. Use it when the format genuinely has no discriminator, and prefer a tagged form whenever you have the choice.

Errors that point at the problem

serde_json::Error carries the location and the category, which is what turns "invalid JSON" into a message someone can act on. 

match serde_json::from_str::<Package>(data) {
    Ok(pkg) => println!("{pkg:?}"),
    Err(e) => {
        // Both are 1-based and point into the input text.
        eprintln!("line {}, column {}: {e}", e.line(), e.column());

        if e.is_syntax() {
            eprintln!("  the text is not valid JSON at all");
        } else if e.is_data() {
            eprintln!("  valid JSON, but not the shape Package expects");
        } else if e.is_eof() {
            eprintln!("  the input ended in the middle of a value");
        }
    }
}

Reading more JSON than fits in memory

Two shapes come up constantly. JSON Lines — one document per line — is the simpler and more common of the two, and needs nothing special: 

use std::fs::File;
use std::io::{BufRead, BufReader};

let reader = BufReader::new(File::open("events.jsonl")?);

for line in reader.lines() {
    let line = line?;
    if line.trim().is_empty() { continue; }

    let event: Event = serde_json::from_str(&line)?;
    handle(event);
}

For a stream of concatenated JSON values with no line structure, serde_json has a dedicated iterator: 

use std::io::BufReader;

let reader = BufReader::new(File::open("stream.json")?);

// Yields Result<Event, Error> one document at a time; peak memory
// stays proportional to a single document, not the whole file.
let stream = serde_json::Deserializer::from_reader(reader).into_iter::<Event>();

for item in stream {
    handle(item?);
}
Large integers deserve a thought

JSON's spec puts no limit on numbers, but many producers are JavaScript, where integers above 253 silently lose precision. serde_json itself handles full u64 and i64 ranges correctly, and the arbitrary_precision feature keeps the exact text of any number. If you are exchanging large IDs with a JavaScript client, the usual fix is to send them as strings.

One derive, many formats

Because serde is format-agnostic, the same #[derive(Serialize, Deserialize)] already works with toml for config files, rmp-serde for MessagePack, ciborium for CBOR, bincode for a compact binary form, and the csv crate on the Databases & CSV page. It is also what reqwest's .json() uses on the HTTP page. Describing your data once and reusing it everywhere is the whole point of the design.

Strings Before You Reach for Regex

Rust's string handling is strict in ways that feel obstructive for a week and then quietly prevent a whole category of bugs. It is also rich enough that a surprising share of "I need a regex here" moments turn out not to.

Two types, one job

String &str
Owns its bytes? Yes — a heap buffer it will free No — a borrowed view
Growable? Yes: push_str, push No, fixed length
Layout Pointer + capacity + length (3 words) Pointer + length (2 words)
Where it comes from String::from, format!, .to_string() Literals, slicing, &my_string
Use in a parameter Only when the function keeps it Almost always — a &String coerces to it automatically

The relationship is exactly Vec<T> to &[T] from the Collections page — and a String really is a Vec<u8> with one extra promise: its bytes are always valid UTF-8.

That promise has consequences

let s = "Grüße, Jürgen ❤";

// len() counts BYTES, not characters. It always has.
assert_eq!(s.len(), 20);
assert_eq!(s.chars().count(), 15);

// You cannot index a string by character position — there is no
// O(1) answer, so Rust does not offer a misleading one.
// let c = s[3];        // does not compile
let c = s.chars().nth(3);  // Option<char>, and it walks the string

// Slicing uses BYTE offsets and panics if one lands mid-character.
let word = "café";          // 5 bytes: c a f + 2 for é
assert_eq!(&word[0..3], "caf");
// let bad = &word[0..4];  // PANIC: byte index 4 is inside 'é'

// Three ways to walk it, three different answers:
for b in word.bytes()       { /* 5 iterations, u8   */ }
for c in word.chars()       { /* 4 iterations, char */ }
for (i, c) in word.char_indices() { /* byte offset + char */ }
A char is still not "what a user sees"

A char is one Unicode scalar value, four bytes wide. That is not the same as a grapheme cluster — the thing a reader would call a character. "é" may be one scalar or two (e + combining accent), and a flag emoji is several. When you need to count or truncate the way a human would, use the unicode-segmentation crate's .graphemes(true). Truncating a display name by bytes or chars is how you end up printing half an emoji.

The method vocabulary

Learn this table and most of your pattern-matching needs disappear — these are faster than a regex, cannot fail to compile at runtime, and read better.

Method Does
trim(), trim_start(), trim_end() Remove surrounding whitespace. trim_matches(char) removes something else.
split(pat), splitn(n, pat) Iterator of pieces. The pattern can be a char, a &str, or a closure over char.
split_once(pat) / rsplit_once(pat) Split into exactly two at the first / last occurrence. Returns Option<(&str, &str)> — perfect for key=value.
split_whitespace(), lines() The two splits you want most often, handling runs of spaces and \r\n correctly.
strip_prefix(p) / strip_suffix(p) Remove it and return Some(rest), or None if it was not there. Tests and removes in one step.
starts_with, ends_with, contains Boolean tests.
find(pat) / rfind(pat) Option<usize> — a byte offset, ready for slicing.
replace(from, to) / replacen(from, to, n) New String with substitutions.
to_lowercase() / to_uppercase() Unicode-correct, and allocates. to_ascii_lowercase() is cheaper when the input really is ASCII.
parse::<T>() Text to any type implementing FromStr, returning a Result.
repeat(n), concat(), join(sep) Building strings from pieces. 
// Parsing a config line — no regex required.
for line in text.lines() {
    let line = line.trim();

    // Skip blanks and comments.
    if line.is_empty() || line.starts_with('#') {
        continue;
    }

    // split_once handles "key = value with = signs in it" correctly,
    // because it splits only at the FIRST separator.
    let Some((key, value)) = line.split_once('=') else {
        eprintln!("skipping malformed line: {line}");
        continue;
    };

    println!("{} = {}", key.trim(), value.trim());
}

// Stripping a flag prefix, testing and removing in one move.
if let Some(name) = arg.strip_prefix("--") {
    println!("long option: {name}");
}

Building strings without waste

use std::fmt::Write; // needed for write!/writeln! into a String

// SLOW: `out + w` consumes and reallocates on every iteration.
let mut out = String::new();
for w in &words { out = out + w + " "; }

// GOOD: one buffer, sized up front, appended in place.
let mut out = String::with_capacity(words.len() * 8);
for w in &words {
    out.push_str(w);
    out.push(' ');
}

// BEST when a separator is all you need — one allocation, no loop.
let out = words.join(" ");

// Formatting into an existing buffer instead of allocating per line.
let mut report = String::new();
for (name, score) in &results {
    writeln!(report, "{name:<20} {score:>6.1}").unwrap(); // cannot fail for String
}
Cow: pay only when you change something

A function that might need to modify a string can return Cow<str> — "clone on write" — and allocate only in the branch that actually does. This is not an exotic type: it is what Regex::replace_all returns in the next section, which is why replacing nothing costs nothing. 

use std::borrow::Cow;

fn slugify(input: &str) -> Cow<'_, str> {
    if input.contains(' ') {
        Cow::Owned(input.replace(' ', "-"))  // allocates, but only here
    } else {
        Cow::Borrowed(input)                // no allocation at all
    }
}

Regular Expressions

Regular expressions are not in the standard library either. The regex crate is the de facto standard, maintained by the same author as ripgrep — and it makes a promise that most other regex engines cannot. 

[dependencies]
regex = "1"
The linear-time guarantee

The crate documents a hard complexity bound: searching is O(m × n), where m is the size of the pattern and n the size of the text. It compiles patterns to finite automata rather than backtracking, so catastrophic backtracking cannot happen. The pattern (a+)+$ against a long string of as followed by a non-a — a classic exponential-time near miss in backtracking engines — still runs in linear time here.

That matters beyond curiosity: it means a regex applied to untrusted input is not a denial-of-service vector. Catastrophic-backtracking ReDoS, an entire vulnerability class elsewhere, simply does not exist in this crate.

What that guarantee costs

Linear time is only achievable by giving up features that require backtracking. The regex crate therefore has no lookaround ((?=…), (?!…), (?<=…), (?<!…)) and no backreferences (\1). Regex::new returns an Err if you use them, rather than failing mysteriously later.

When you genuinely need those, the fancy-regex crate wraps this one and adds a backtracking engine for the constructs it cannot handle — accepting the exponential worst case in exchange. Most of the time, restructuring the pattern or doing one extra check in Rust is the better answer.

Testing and locating

use regex::Regex;

// ALWAYS use a raw string r"..." for patterns. In a normal string,
// \d is an unknown escape and will not compile.
let re = Regex::new(r"^\d{4}-\d{2}-\d{2}$").unwrap();

assert!(re.is_match("2026-08-20"));
assert!(!re.is_match("20 August 2026"));

// find() gives the first match, with its byte offsets.
let words = Regex::new(r"\b\w{5,}\b").unwrap();
let hay = "the borrow checker prevents dangling pointers";

if let Some(m) = words.find(hay) {
    println!("{:?} at bytes {}..{}", m.as_str(), m.start(), m.end());
    // "borrow" at bytes 4..10
}

// find_iter() walks every non-overlapping match.
let found: Vec<&str> = words.find_iter(hay).map(|m| m.as_str()).collect();
assert_eq!(found, vec!["borrow", "checker", "prevents", "dangling", "pointers"]);

// Splitting on a pattern rather than a fixed separator.
let sep = Regex::new(r"[\s,]+").unwrap();
let fields: Vec<&str> = sep.split("a, b ,c   d").collect();
assert_eq!(fields, vec!["a", "b", "c", "d"]);
new returns a Result for a reason

A pattern is compiled at runtime, so an invalid one is a runtime error. In the examples here .unwrap() is fine because the pattern is a literal that either always works or never does — you will find out the first time you run the program. If the pattern comes from a user or a config file, handle the Err properly and show them what was wrong.

Pulling the pieces out

Capture groups are what turn a regex from a test into a parser. Name them — positional indices become unreadable as soon as the pattern grows. 

use regex::Regex;

// (?<name>...) names a group. (?:...) groups WITHOUT capturing,
// which is what you want for grouping used only by an alternation.
let re = Regex::new(r"(?<year>\d{4})-(?<month>\d{2})-(?<day>\d{2})").unwrap();
let hay = "released 2026-08-20, patched 2026-09-01";

if let Some(caps) = re.captures(hay) {
    // Group 0 is always the whole match.
    println!("matched: {}", &caps[0]);

    // Indexing by name is concise but PANICS if the group did not
    // participate in the match.
    println!("year: {}", &caps["year"]);

    // .name() returns Option<Match> and never panics — the right
    // choice for any group inside an alternation or a `?`.
    if let Some(m) = caps.name("month") {
        println!("month {} at bytes {}..{}", m.as_str(), m.start(), m.end());
    }
}

// Every match, with its groups.
for caps in re.captures_iter(hay) {
    println!("{}/{}/{}", &caps["day"], &caps["month"], &caps["year"]);
}
// 20/08/2026
// 01/09/2026
A matched group is still just text

\d{4} guarantees four digits, not a valid year — and certainly not an i32. You still have to .parse(), and you still have to handle the failure. A regex validates shape; your code validates meaning.

Rewriting text

use regex::Regex;

let re = Regex::new(r"(?<y>\d{4})-(?<m>\d{2})-(?<d>\d{2})").unwrap();

// $name (or $1, $2…) expands a capture group in the replacement.
let out = re.replace_all("due 2026-08-20", "$m/$d/$y");
assert_eq!(out, "due 08/20/2026");

// Use ${name} when the next character could be read as part of the
// name: "$mX" looks for a group called "mX", "${m}X" does not.
let out = re.replace_all("due 2026-08-20", "${m}-${d}");

// replace() changes only the first match; replace_all() changes all;
// replacen(hay, n, rep) changes the first n.

// A closure gets the Captures, for anything the pattern cannot say.
let masked = re.replace_all("born 1984-04-01", |caps: &regex::Captures| {
    format!("{}-**-**", &caps["y"])
});
assert_eq!(masked, "born 1984-**-**");
Replacing nothing allocates nothing

replace_all returns Cow<str> — the type from the previous section. When the pattern does not match, you get Cow::Borrowed pointing at the original text and no allocation happens at all. It only builds a new String when there is genuinely something to change.

Compile the pattern once, not once per call

This is the single most important performance rule for the crate, and the easiest to get wrong. Regex::new builds a state machine — an expensive operation, frequently far more expensive than the search you are about to perform. 

use regex::Regex;

// SLOW: recompiles the pattern on every single call. In a loop this
// can dominate the runtime completely.
fn is_email_slow(candidate: &str) -> bool {
    Regex::new(r"^[^@\s]+@[^@\s]+\.[^@\s]+$").unwrap().is_match(candidate)
}
use std::sync::LazyLock;
use regex::Regex;

// FAST: compiled on first use, then shared for the life of the
// program. LazyLock is in std as of Rust 1.80 — no crate needed.
static EMAIL: LazyLock<Regex> = LazyLock::new(|| {
    Regex::new(r"^[^@\s]+@[^@\s]+\.[^@\s]+$").unwrap()
});

fn is_email(candidate: &str) -> bool {
    EMAIL.is_match(candidate)
}

A Regex is Send + Sync, so one static is safely shared across every thread — no locking, no per-thread copy. Before Rust 1.80 the same pattern used once_cell::sync::Lazy, which you will still see in older code and which works identically.

And do not build a pattern from user input by hand

format!("^{user_input}$") lets someone inject regex syntax — the same category of mistake as string-concatenating SQL on the Databases page. Escape it with regex::escape(user_input), which returns a pattern matching that text literally.

Flags

Flags go inside the pattern as (?flags) at the start, or scoped to a group as (?flags:…).

Flag Effect
(?i) Case-insensitive, and Unicode-aware about it.
(?m) Multi-line: ^ and $ match at line boundaries.
(?s) Let . match a newline as well.
(?x) Verbose: ignore whitespace in the pattern and allow # comments.
(?U) Swap greedy and lazy, so * becomes lazy and *? greedy.

The verbose flag is worth adopting as a habit. A commented pattern is reviewable; a dense one is not. 

let phone = Regex::new(r"(?x)
    (?<area>\d{3})     # area code
    [\s.\-]?           # optional separator
    (?<prefix>\d{3})   # exchange
    [\s.\-]?
    (?<line>\d{4})     # subscriber number
").unwrap();

Testing many patterns at once

RegexSet checks a whole list of patterns in a single pass over the text, rather than running each one separately. It tells you which matched, not where. 

use regex::RegexSet;

let set = RegexSet::new([
    r"^GET ",
    r"\.css$",
    r"\d{3}$",
]).unwrap();

let hits: Vec<usize> = set.matches("GET /style.css").into_iter().collect();
assert_eq!(hits, vec![0, 1]); // patterns 0 and 1 matched, 2 did not

Two variants worth knowing

  • regex::bytes::Regex — searches &[u8] instead of &str, for data that is not guaranteed to be valid UTF-8. Same API, byte-oriented matches.
  • regex-lite — a separate crate with the same core API, far fewer dependencies and a much smaller binary, at the cost of speed and Unicode features. Worth considering for the WebAssembly target, where binary size is the thing you are optimising.
When not to use a regex at all

A regex describes a regular language. Nested structures are not regular, and no amount of cleverness makes them so:

  • JSON → serde_json, at the top of this page.
  • HTML or XML → scraper, html5ever, quick-xml. Never a regex.
  • CSV → the csv crate on the Databases & CSV page. Quoted fields containing commas and newlines defeat the obvious pattern.
  • URLs → the url crate, which implements the actual spec.
  • Dates → chrono or time, which know that 2026-02-30 is shaped correctly and still wrong.
  • A fixed prefix, suffix or separator → strip_prefix, split_once and friends from the previous section. Faster, clearer, and they cannot fail to compile.

Putting It Together

Here is the whole page in one program: read semi-structured text, pull it apart with a named-group regex compiled exactly once, and emit clean JSON. This is a large share of what real data-plumbing code does. 

[dependencies]
regex      = "1"
serde      = { version = "1", features = ["derive"] }
serde_json = "1"
use regex::Regex;
use serde::Serialize;
use std::sync::LazyLock;

// Compiled once, on first use. The (?x) flag lets the pattern be
// laid out and commented like ordinary code.
static LOG_LINE: LazyLock<Regex> = LazyLock::new(|| {
    Regex::new(
        r#"(?x)
        ^(?<ip>\S+)\s+            # client address
        \S+\s+\S+\s+              # identity and user, usually "-"
        \[(?<time>[^\]]+)\]\s+    # timestamp in brackets
        "(?<method>[A-Z]+)\s      # request method
        (?<path>\S+)[^"]*"\s+     # path, then the protocol we ignore
        (?<status>\d{3})\s+       # status code
        (?<bytes>\d+)$            # response size
        "#,
    )
    .expect("the log pattern is a literal and must compile")
});

// The struct borrows from the input line rather than copying it —
// Match::as_str() hands back a slice tied to the original text.
#[derive(Debug, Serialize)]
struct Entry<'a> {
    ip: &'a str,
    time: &'a str,
    method: &'a str,
    path: &'a str,
    status: u16,
    bytes: u64,
}

// Returning Option lets `?` skip any line that does not fit,
// without a single explicit `if`.
fn parse_line(line: &str) -> Option<Entry<'_>> {
    let caps = LOG_LINE.captures(line)?;

    Some(Entry {
        ip: caps.name("ip")?.as_str(),
        time: caps.name("time")?.as_str(),
        method: caps.name("method")?.as_str(),
        path: caps.name("path")?.as_str(),
        // Matching \d{3} proves the shape; parsing proves the value.
        status: caps["status"].parse().ok()?,
        bytes: caps["bytes"].parse().ok()?,
    })
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let log = r#"10.0.0.7 - - [20/Aug/2026:13:55:36 +0000] "GET /index.html HTTP/1.1" 200 5120
10.0.0.9 - - [20/Aug/2026:13:55:41 +0000] "POST /api/login HTTP/1.1" 401 96
this line is not a log entry at all
10.0.0.7 - - [20/Aug/2026:13:56:02 +0000] "GET /style.css HTTP/1.1" 200 1840"#;

    // filter_map drops the lines that did not parse and keeps the rest.
    let entries: Vec<Entry> = log.lines().filter_map(parse_line).collect();

    println!("parsed {} of {} lines", entries.len(), log.lines().count());

    // Serialize the whole batch as a JSON array.
    println!("{}", serde_json::to_string_pretty(&entries)?);

    // Or as JSON Lines, which streams and appends nicely.
    for entry in &entries {
        println!("{}", serde_json::to_string(entry)?);
    }

    Ok(())
}

Output of the pretty-printed array:

[
  {
    "ip": "10.0.0.7",
    "time": "20/Aug/2026:13:55:36 +0000",
    "method": "GET",
    "path": "/index.html",
    "status": 200,
    "bytes": 5120
  },
  /* … two more entries … */
]
Three details worth stealing
  • Entry<'a> borrows. No String is allocated per field. Serialize works perfectly well on borrowed data, so the JSON output costs one allocation rather than six per line.
  • Option plus filter_map. A line that does not match returns None and disappears. No sentinel values, no flags, no nested if.
  • The pattern is data, the parsing is code. The regex extracts substrings; parse() turns them into numbers and reports failure. Keeping that boundary clean is what stops a pattern from growing into something unreadable.
