Files & I/O in Rust

Safe, portable filesystem work with std::fs, std::path and std::io — and the error handling that makes it trustworthy.

On this page

Why paths are their own type, and never plain Strings.
Reading whole files, and streaming ones too big to hold in memory.
Writing, appending, buffering — and what actually reaches the disk.
Handling io::Error in a way that tells the user something useful.

Paths Are Not Strings

Most languages treat a filesystem path as a string. Rust does not, and the reason is that operating systems disagree about what a filename even is.

On Unix, a filename is an arbitrary sequence of bytes — anything except a null byte or a slash — and is not required to be valid UTF-8. On Windows, a filename is a sequence of 16-bit code units that is usually, but not always, valid UTF-16; unpaired surrogates are legal on disk. Neither maps cleanly onto Rust's String, which guarantees valid UTF-8. So the standard library provides a parallel family of types:

Purpose Borrowed (unsized) Owned (heap) Encoding guarantee
Text str String Always valid UTF-8
OS string OsStr OsString Whatever the platform permits
Filesystem path Path PathBuf An OsStr, plus path-aware methods

The pairing mirrors str/String exactly: Path is a borrowed view and PathBuf is the growable owned form. In practice you take &Path (or better, impl AsRef<Path>) as a parameter and return PathBuf. 

use std::path::{Path, PathBuf};

let path = Path::new("projects/rust/readme.md");

// Inspecting the parts — each returns an Option, because not every
// path has a parent, a file name, or an extension.
assert_eq!(path.parent(),         Some(Path::new("projects/rust")));
assert_eq!(path.file_name(),      Some("readme.md".as_ref()));
assert_eq!(path.file_stem(),      Some("readme".as_ref()));
assert_eq!(path.extension(),      Some("md".as_ref()));

// Building paths: join() inserts the platform's separator for you.
// Never concatenate path strings by hand — that is how a program
// works on your machine and breaks on someone else's.
let mut target = PathBuf::from("output");
target.push("2026");
target.push("report.csv");
// or, as one expression:
let target = Path::new("output").join("2026").join("report.csv");

// Queries that touch the filesystem (and so can be wrong a moment later)
let exists = path.exists();
let is_file = path.is_file();

// Printing: a path may not be valid UTF-8, so it does not implement
// Display directly. `display()` gives a lossy but printable view.
println!("{}", path.display());
Accept AsRef<Path> in your own functions

Every std::fs function is generic over AsRef<Path>, which is why you can pass a &str, a String, a &Path or a PathBuf interchangeably. Do the same in your own code and callers never have to convert: 

fn load<P: AsRef<Path>>(path: P) -> std::io::Result<String> {
    std::fs::read_to_string(path)
}

load("config.toml")?;                     // &str
load(String::from("config.toml"))?;       // String
load(Path::new("config.toml"))?;          // &Path

Reading Files

The right approach depends entirely on one question: do you know the file is small?

Read it all into memory

For a config file, a template or a small data file, one call does everything: open, read to the end, validate the UTF-8, and close. 

use std::fs;

fn read_config() -> std::io::Result<String> {
    // `?` propagates a missing file, a permission error, or invalid UTF-8.
    let contents = fs::read_to_string("config.toml")?;
    Ok(contents)
}

// The file is closed automatically when the internal File handle is
// dropped at the end of read_to_string. There is nothing to remember
// to close, and no `finally` block to get wrong.
Know the size before you do this

read_to_string allocates enough memory to hold the entire file. On a multi-gigabyte log, or on any file whose size is chosen by someone else, that is a straightforward way to have your process killed. If the size is not bounded by something you control, use the streaming approach in the next tab.

Files known at compile time

For data that ships with the binary — a default config, a lookup table, an SQL schema — include_str!("default.toml") embeds the file's contents as a &'static str at compile time. No I/O at runtime, and no way for the file to go missing. include_bytes! does the same for binary data.

Stream it with BufReader

A bare File is unbuffered: every small read is a system call, and system calls are expensive. Wrapping it in a BufReader reads a block at a time (8 KiB by default) and serves your reads from that buffer. 

use std::fs::File;
use std::io::{BufRead, BufReader};
use std::path::Path;

fn count_matching(path: &Path, needle: &str) -> std::io::Result<usize> {
    let file = File::open(path)?;
    let reader = BufReader::new(file);
    let mut hits = 0;

    // lines() yields io::Result<String> — one allocation per line, and
    // the trailing \n (or \r\n) is stripped for you.
    for line in reader.lines() {
        let line = line?;     // an I/O error mid-file is still possible
        if line.contains(needle) {
            hits += 1;
        }
    }

    Ok(hits)
}

Because lines() is an iterator, everything from the Collections & Iterators page applies — memory stays flat no matter how large the file is: 

let total: f64 = BufReader::new(File::open(path)?)
    .lines()
    .filter_map(|line| line.ok())
    .filter(|line| !line.starts_with('#'))
    .filter_map(|line| line.trim().parse::<f64>().ok())
    .sum();
Reuse one buffer for the hottest loops

lines() allocates a fresh String per line. When that shows up in a profile, switch to reader.read_line(&mut buf) with a single String you clear() each time — the same trick as reusing a StringRecord on the CSV page.

When it is not text

Images, archives and binary formats are just bytes, and forcing them through a UTF-8 check would fail. Use the Vec<u8> variants. 

use std::fs::File;
use std::io::{BufReader, Read};

// Whole file as bytes — the binary counterpart of read_to_string.
let data: Vec<u8> = std::fs::read("logo.png")?;

// A fixed-size header, without loading the rest.
let mut reader = BufReader::new(File::open("logo.png")?);
let mut magic = [0u8; 8];
reader.read_exact(&mut magic)?;   // errors if the file is shorter

if &magic == b"\x89PNG\r\n\x1a\n" {
    println!("this really is a PNG");
}

// Streaming in fixed-size chunks, for hashing or copying.
let mut buffer = [0u8; 8192];
loop {
    let n = reader.read(&mut buffer)?;
    if n == 0 {
        break; // 0 bytes read means end of file
    }
    process(&buffer[..n]); // only the first n bytes are valid
}
read may return fewer bytes than you asked for

A short read is not an error — it is normal, especially on pipes and sockets. Always use the returned count to slice the buffer, and use read_exact when you genuinely need a specific number of bytes.

Reading from standard input

A Unix-style tool should read a file when given one and standard input when not. Rust makes that natural, because Read is a trait rather than a concrete type. 

use std::io::{self, BufRead, BufReader, Read};
use std::fs::File;

// Return a boxed reader so the caller does not care which it got.
fn open_input(path: Option<&str>) -> io::Result<Box<dyn BufRead>> {
    match path {
        Some("-") | None => Ok(Box::new(BufReader::new(io::stdin()))),
        Some(p)          => Ok(Box::new(BufReader::new(File::open(p)?))),
    }
}

fn main() -> io::Result<()> {
    // args().nth(1) is the first argument; nth(0) is the program name.
    let arg = std::env::args().nth(1);
    let reader = open_input(arg.as_deref())?;

    for line in reader.lines() {
        println!("{}", line?.to_uppercase());
    }
    Ok(())
}

Now cargo run -- notes.txt and cat notes.txt | cargo run both work, and the body of the program never had to know the difference.

Writing Files

File::create opens a file write-only, creating it if needed and truncating it to zero bytes if it already exists. That last part surprises people, so say it out loud: File::create on an existing file destroys its contents. When you need anything else, use OpenOptions. 

use std::fs::{self, File, OpenOptions};
use std::io::{BufWriter, Write};

// The one-liner: create (or truncate) and write, all at once.
fs::write("greeting.txt", "Hello, world!\n")?;

// Appending, with OpenOptions' builder API.
fn append_log(message: &str) -> std::io::Result<()> {
    let mut file = OpenOptions::new()
        .create(true)   // make it if it does not exist
        .append(true)   // every write goes to the end (implies .write(true))
        .open("system.log")?;

    writeln!(file, "{message}")?; // like println!, but to a writer
    Ok(())
}
OpenOptions flag Effect
.read(true) Allow reading from the handle.
.write(true) Allow writing, starting at the beginning.
.append(true) Every write goes to the end, regardless of seeking. Implies write.
.truncate(true) Empty the file on open. Requires write.
.create(true) Create it if absent, open it if present.
.create_new(true) Create it, and fail if it already exists. Atomic, so it is the safe way to claim a lock file or avoid clobbering someone else's output.

Buffering, flushing, and what "saved" means

Writing many small pieces to a bare File means one system call each. Wrap it in a BufWriter and they are batched. But buffering introduces a question that matters: when is the data actually safe? 

use std::fs::File;
use std::io::{BufWriter, Write};

fn write_report(rows: &[(String, u32)]) -> std::io::Result<()> {
    let file = File::create("report.txt")?;
    let mut out = BufWriter::new(file);

    for (name, score) in rows {
        writeln!(out, "{name}\t{score}")?;   // into the buffer, usually no syscall
    }

    // Flush EXPLICITLY. BufWriter also flushes when dropped, but a drop
    // cannot return an error — so a disk-full failure at the very end
    // would be silently discarded. Calling flush() surfaces it here.
    out.flush()?;
    Ok(())
}
flush is not fsync

flush() pushes your program's user-space buffer into the operating system. It does not guarantee the bytes reached the physical disk — the OS still has its own page cache, and a power cut can lose them. (On a bare File, which has no user-space buffer, flush() does nothing at all.) When durability genuinely matters, call file.sync_all(), which asks the operating system to commit the data and metadata to storage before returning.

Writing a file without ever leaving it half-written

If your program dies mid-write, a reader may find a truncated file. The standard fix is write-then-rename: on the same filesystem, a rename is atomic, so a reader sees either the old file or the complete new one, never something in between. Replacing an existing file with std::fs::rename is platform-specific, though: Unix replaces the destination, while Windows fails if the destination already exists. 

use std::fs;
use std::io::Write;

fn save_atomically(path: &str, contents: &str) -> std::io::Result<()> {
    let temp = format!("{path}.tmp");

    {
        let mut file = fs::File::create(&temp)?;
        file.write_all(contents.as_bytes())?;
        file.sync_all()?;   // data is on disk before we swap it in
    }                       // file closed here

    fs::rename(&temp, path) // atomic on the same filesystem; see Windows caveat above
}

Directories and Metadata

std::fs wraps the platform's directory system calls behind one portable API.

Listing a directory

fs::read_dir returns an iterator of io::Result<DirEntry> — the inner Result is there because a single entry can fail even after the directory opened successfully. The . and .. entries are never yielded. 

use std::fs;

fn list_rust_files() -> std::io::Result<()> {
    for entry in fs::read_dir("src")? {
        let entry = entry?;
        let path = entry.path();

        // file_type() can avoid a second stat() call on platforms that expose it
        if entry.file_type()?.is_file()
            && path.extension() == Some("rs".as_ref())
        {
            println!("{}", path.display());
        }
    }
    Ok(())
}

read_dir is not recursive and the order is unspecified. For a recursive walk, sort the entries yourself or use the walkdir crate, which also handles symlink loops and depth limits.

Common operations

use std::fs;

fn housekeeping() -> std::io::Result<()> {
    // Create a directory and any missing parents.
    // Unlike create_dir, this is not an error if it exists.
    fs::create_dir_all("backup/logs")?;

    // Copy a file; returns the number of bytes copied.
    let bytes = fs::copy("system.log", "backup/logs/system.log")?;
    println!("copied {bytes} bytes");

    // Rename, or move. Atomic within one filesystem; across
    // filesystems it fails, and you must copy then delete.
    fs::rename("draft.txt", "backup/final.txt")?;

    // Delete a single file…
    fs::remove_file("system.log")?;

    // …an empty directory…
    fs::remove_dir("empty_folder")?;

    // …or a directory and everything inside it. No confirmation,
    // no undo. Be certain the path is what you think it is.
    fs::remove_dir_all("backup/old")?;

    Ok(())
}

Metadata

use std::fs;

let meta = fs::metadata("report.txt")?;   // follows symlinks

println!("size:      {} bytes", meta.len());
println!("directory: {}", meta.is_dir());
println!("read-only: {}", meta.permissions().readonly());

// Timestamps are Option-like: not every platform records every one.
if let Ok(modified) = meta.modified() {
    println!("modified:  {modified:?}");
}

// symlink_metadata describes the link itself rather than its target.
let link_meta = fs::symlink_metadata("shortcut")?;
println!("is a symlink: {}", link_meta.file_type().is_symlink());

Handling I/O Errors Well

Every fallible operation here returns std::io::Result<T>, which is just Result<T, std::io::Error>. Propagating it with ? is the right default — but the error carries a kind(), and using it is what separates a useful program from one that only says "error". 

use std::fs::File;
use std::io::{self, ErrorKind};

fn open_or_create(path: &str) -> io::Result<File> {
    match File::open(path) {
        Ok(file) => Ok(file),

        Err(e) => match e.kind() {
            // Absent is fine — make it.
            ErrorKind::NotFound => File::create(path),

            // Present but unreadable is worth a clearer message.
            ErrorKind::PermissionDenied => Err(io::Error::new(
                ErrorKind::PermissionDenied,
                format!("cannot read {path}: check the file's permissions"),
            )),

            // Anything else: pass it along untouched.
            _ => Err(e),
        },
    }
}
Do not check, then act

if path.exists() { File::open(path) } looks careful but is a race: the file can be deleted, created or replaced between the two calls. This is the classic time-of-check to time-of-use bug, and on a shared directory it is a security problem, not just a flaky one. Just perform the operation and handle its error — the operating system does the check and the action together, atomically.

Say which file failed

An io::Error knows the reason but not the path, so a bare propagation gives the user "No such file or directory" with no clue which one. Add context at the point where you still know it — the anyhow crate makes this a one-liner: 

use anyhow::{Context, Result};

fn load_settings(path: &str) -> Result<String> {
    std::fs::read_to_string(path)
        .with_context(|| format!("failed to read settings from {path}"))
}

// The user now sees:
//   Error: failed to read settings from /etc/app/settings.toml
//   Caused by: No such file or directory (os error 2)
main can return a Result

Writing fn main() -> std::io::Result<()> lets you use ? at the top level. On an Err, Rust prints the error's Debug form to standard error and exits with a non-zero status — exactly what a shell script calling your tool expects.
