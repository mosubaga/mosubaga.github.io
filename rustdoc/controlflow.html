The Expression-Based Paradigm

In C, Java or Python there is a firm line between statements, which do something, and expressions, which evaluate to a value. Rust moves that line: nearly every construct in the language — if, match, a bare block, even loop — is an expression that produces a value you can bind or return. 

let condition = true;

// The whole if/else evaluates to one value, bound to `number`.
let number = if condition { 5 } else { 10 };

// A plain block is an expression too — handy for scoping temporaries.
let area = {
    let width = 4;
    let height = 7;
    width * height   // no semicolon: this is the block's value
};

println!("{number} and {area}"); // 5 and 28
The semicolon rule

Leaving the semicolon off the final line of a block makes that line the block's value. Adding one turns it into a statement, and the block evaluates to the unit type () instead. That single character is behind a large share of "expected i32, found ()" errors in your first week — and the compiler will usually tell you to remove it.

Every branch must agree

Because if is an expression, all of its arms must produce the same type. let x = if c { 5 } else { "five" }; does not compile. Nor does an if with no else used as a value — the missing branch would yield ().

Variables and Bindings

Rust calls this variable binding rather than assignment, and the distinction matters: a binding associates a name with a value and with responsibility for that value's memory.

1. Immutable by default Safety

Bindings cannot be reassigned unless declared mut. Mutability is also inherited: marking a struct binding mut makes all of its fields mutable through that binding. 

let x = 5;
// x += 1;
// ERROR: cannot assign twice to
//        immutable variable `x`

let mut y = 5;
y += 1;    // fine

2. Static typing with inference Ergonomics

Every value has a type known at compile time, but you rarely write it down. The compiler infers types from how a value is used — including across function boundaries within a body. 

let deduced = 10;          // i32 by default
let explicit: u64 = 100;
let pi = 3.14;              // f64 by default

// Sometimes inference needs a hint —
// parse() could produce many types:
let n: i32 = "42".parse().unwrap();
let m = "42".parse::<i32>().unwrap();

3. No uninitialised reads Safety

In C, reading an uninitialised variable is undefined behaviour. Rust's compiler tracks initialisation through every path and refuses to compile a read that might happen first. 

let value: i32;   // declared, not set

// println!("{value}");
// ERROR: used binding `value` is
//        possibly-uninitialized

value = 42;         // initialised here
println!("{value}"); // now fine

4. Shadowing Ergonomics

You may declare a new binding with an existing name. The old value is shadowed — not mutated — so the new one can have a completely different type. It saves inventing names like input_str and input_parsed. 

let data_len = "81";        // &str
let data_len: usize =
    data_len.parse().unwrap(); // usize

println!("{data_len}");      // 81

5. Move versus copy Ownership

Assigning a heap-owning value moves it: ownership transfers and the source binding becomes unusable. Small types that live entirely on the stack implement Copy and are duplicated bitwise instead. 

// MOVE
let s1 = String::from("ramen");
let s2 = s1;
// println!("{s1}"); // ERROR:
//   borrow of moved value: `s1`

// COPY
let n1: i32 = 36;
let n2 = n1;
println!("{n1} {n2}"); // both live

6. const versus static Scope

Both live outside functions and both need an explicit type. A const is evaluated at compile time and inlined at each use site; a static is a single fixed location in memory with a 'static lifetime. 

const BUFFER_SIZE: usize = 1024;
static APP_NAME: &str = "widget";

// Mutable global state uses an atomic
// or a Mutex — see the note below.
use std::sync::atomic::{AtomicBool, Ordering};
static IN_ERROR: AtomicBool =
    AtomicBool::new(false);

IN_ERROR.store(true, Ordering::Relaxed);
Do not reach for static mut

You will still find static mut in older tutorials. It is genuinely dangerous — unsynchronised access from multiple threads is undefined behaviour — and Rust has been closing it off: in the 2024 edition, creating a reference to a static mut is a hard error, and reading or writing one directly still requires unsafe. Use AtomicUsize / AtomicBool for counters and flags, Mutex<T> or RwLock<T> for anything larger, and OnceLock<T> for a value initialised once and then only read.

The primitive types worth memorising

Category Types Notes
Signed integers i8, i16, i32, i64, i128, isize i32 is the default and usually the fastest choice.
Unsigned integers u8, u16, u32, u64, u128, usize usize matches the pointer width and is what indexing and .len() use.
Floating point f32, f64 f64 is the default.
Boolean bool Only true and false. No integer ever converts implicitly.
Character char Four bytes, holding one Unicode scalar value — so 'ß', 'あ' and '🦀' are each a single char.
Compound (T, U), [T; N] Tuples group different types; arrays hold N values of one type, with N fixed at compile time.
Overflow behaves differently per profile

In a debug build, integer overflow panics. In a release build it wraps using two's complement, because the check costs performance. Neither is undefined behaviour. When the behaviour matters, say so explicitly with wrapping_add, checked_add (returns Option), saturating_add or overflowing_add.

Conditional Branching

if, else if and else look familiar, with two rules enforced that most languages leave loose:

  • No implicit truthiness. The condition must be a bool. A non-zero integer, a non-empty string and a non-null pointer are all rejected — write the comparison you mean.
  • Braces are required, parentheses are not. if x > 3 { … }. Because every block is braced, the dangling-else and "I added a second line to the body" bug classes simply cannot occur.

Ordinary branching

let x = 15;

if x % 15 == 0 {
    println!("FizzBuzz");
} else if x % 3 == 0 {
    println!("Fizz");
} else if x % 5 == 0 {
    println!("Buzz");
} else {
    println!("{x}");
}

// The same thing as an expression — note every arm is a &str.
let label = if x % 15 == 0 { "FizzBuzz" }
    else if x % 3 == 0 { "Fizz" }
    else if x % 5 == 0 { "Buzz" }
    else { "none" };
When a chain gets long, reach for match

Four or more else if branches over the same value is usually a match waiting to be written — and match brings exhaustiveness checking with it, so the compiler tells you when you forget a case.

Matching one variant with if let

When you care about exactly one pattern and want to ignore everything else, a full match is noisy. if let is the shorthand. 

let possible_value: Option<i32> = Some(42);

// If it matches Some, bind the inner value to `val` and run the block.
if let Some(val) = possible_value {
    println!("unwrapped: {val}");
}

// An else arm handles the other cases.
if let Ok(port) = "8080".parse::<u16>() {
    println!("listening on {port}");
} else {
    eprintln!("not a valid port number");
}

// It is an expression too, so it can produce a value.
let doubled = if let Some(v) = possible_value { v * 2 } else { 0 };

Early return with let … else

Stabilised in Rust 1.65, let … else solves the awkward case where you want to bind a value on the happy path and bail out otherwise — without the rightward drift of nested if let blocks. The else block must diverge: return, break, continue or panic!. 

// Without let-else: the real work drifts further right each time.
fn describe_old(input: Option<&str>) -> String {
    if let Some(text) = input {
        if let Ok(n) = text.parse::<i32>() {
            format!("got {n}")
        } else {
            "not a number".to_string()
        }
    } else {
        "nothing".to_string()
    }
}

// With let-else: the failures leave early and the happy path stays flat.
fn describe(input: Option<&str>) -> String {
    let Some(text) = input else {
        return "nothing".to_string();
    };

    let Ok(n) = text.parse::<i32>() else {
        return "not a number".to_string();
    };

    // `text` and `n` are in scope for the rest of the function.
    format!("got {n}")
}
Guard clauses, the Rust way

This is the idiom to reach for when validating inputs at the top of a function. Each failure gets its own two lines, the happy path never indents, and you keep the bindings afterwards.

The Three Loops

Rust has exactly three looping constructs, and idiomatic code uses for for the overwhelming majority of cases.

loop — infinite until you say otherwise

loop repeats until a break. It is preferred over while true because the compiler knows it runs at least once, which keeps initialisation analysis happy downstream. Its distinguishing feature: break can carry a value out. 

let mut counter = 0;

let result = loop {
    counter += 1;
    if counter == 10 {
        break counter * 2; // the loop evaluates to 20
    }
};

println!("{result}"); // 20

This makes loop the natural shape for retry-until-success: keep trying, and break out with whatever you eventually got.

while — repeat while a condition holds

let mut n = 5;

while n != 0 {
    println!("{n}...");
    n -= 1;
}

println!("Liftoff!");
Do not use while to walk a collection

The while i < v.len() { … v[i] … } pattern is where off-by-one and out-of-bounds bugs live. Rust turns the latter into a panic rather than memory corruption, but the bug is still a bug. Use for, which cannot go out of bounds at all.

for — the one you will actually use

for works with anything implementing IntoIterator, which the compiler calls to obtain an iterator and then drives with next(). No index variable exists, so no index can be wrong. 

// 1. An exclusive range 0..5, or an inclusive one 1..=5
for i in 1..=5 {
    println!("range value: {i}");
}

let fruits = vec!["apple", "banana", "cherry"];

// 2. Borrow the collection: it stays usable afterwards.
for item in &fruits {
    println!("read-only: {item}");
}

// 3. Borrow mutably to change elements in place.
let mut counts = vec![1, 2, 3];
for n in &mut counts {
    *n *= 10;  // `n` is &mut i32, so dereference to assign
}

// 4. Take ownership: `fruits` is consumed and gone after this.
for item in fruits {
    println!("owned: {item}");
}

// Need the index after all? Ask the iterator for it.
for (i, n) in counts.iter().enumerate() {
    println!("{i}: {n}");
}
The three flavours are a type-level choice

&collection, &mut collection and collection select shared borrow, exclusive borrow and ownership respectively — the same distinction as iter(), iter_mut() and into_iter(). Getting this wrong is the most common early borrow-checker complaint, and there is much more on it on the Collections & Iterators page.

while let — loop as long as a pattern matches

The looping counterpart of if let. It is the natural way to drain a collection, read from a channel, or consume an iterator by hand. 

let mut stack = vec![1, 2, 3];

// pop() returns Option<i32>: Some until empty, then None ends the loop.
while let Some(top) = stack.pop() {
    println!("{top}"); // 3, 2, 1
}

// Reading lines until end of input follows exactly the same shape.
let mut chars = "rust".chars();
while let Some(c) = chars.next() {
    print!("[{c}]");
}

Nested loops and labels

Rust has no goto. To break out of more than the innermost loop, give the outer one a label — an identifier with a leading apostrophe — and name it in the break or continue. 

// Breaks out of the entire nested structure, not just the inner loop.
'outer: for x in 0..10 {
    for y in 0..10 {
        if x * y > 50 {
            println!("stopping at {x} x {y}");
            break 'outer;
        }
        if y == 3 {
            continue 'outer; // next x, skipping the rest of this y
        }
    }
}

// Labels also work on plain blocks, giving a scoped early exit
// that carries a value out — stable since Rust 1.65.
let found = 'search: {
    for (i, c) in "hello world".chars().enumerate() {
        if c == ' ' {
            break 'search Some(i);
        }
    }
    None
};

println!("{found:?}"); // Some(5)

Functions and Methods

Functions are declared with fn, named in snake_case, and always annotate their parameter and return types — type inference stops at the function boundary, which is what keeps error messages local and readable.

Anatomy

Parameters go in parentheses, the return type after ->. Omitting the return type means the function returns the unit type () — Rust's equivalent of void. 

fn greet(name: &str) {
    println!("Hello, {name}!");
}

fn square(n: i32) -> i32 {
    n * n   // no semicolon = return value
}

Returning

The last expression without a semicolon is the return value. return exists for early exits, but idiomatic Rust leaves the final value bare. 

fn classify(score: u32) -> &'static str {
    if score > 100 {
        return "invalid"; // early exit
    }

    if score >= 70 {
        "pass"
    } else {
        "retry"
    }
}

Passing values: move, copy, borrow

Parameters obey the same ownership rules as bindings. This is the single most important thing to get right when designing a function signature, so it is worth seeing all four cases side by side.

Copy: the caller keeps the original

Scalars, char, bool and tuples of them implement Copy, so passing one duplicates it.

fn double(x: i32) -> i32 {
    x * 2
}

let n = 21;
let result = double(n);
println!("n is still {n}, result is {result}");

Move: the function takes ownership

Use this when the function is genuinely consuming the value — storing it, transforming it, or destroying it.

fn consume(text: String) {
    println!("consumed: {text}");
}   // `text` is dropped here — the buffer is freed

let message = String::from("rust");
consume(message);
// println!("{message}"); // ERROR: message was moved

Borrow: read without taking

The default choice for a function that only reads. Prefer &str over &String and &[T] over &Vec<T> — the slice forms accept strictly more callers at no extra cost. 

fn word_count(text: &str) -> usize {
    text.split_whitespace().count()
}

let message = String::from("safe fast productive");
let count = word_count(&message);  // &String coerces to &str
println!("{count} words in {message}"); // message still owned here

Mutable borrow: change it in place

Exclusive for the duration of the call. While this borrow is live, nothing else — including the caller — can read or write the value. 

fn normalize_name(name: &mut String) {
    name.make_ascii_lowercase();
    name.push_str(".rs");
}

let mut crate_name = String::from("MY_TOOL");
normalize_name(&mut crate_name);  // &mut is explicit at the call site too
println!("{crate_name}");           // my_tool.rs

Associated functions and methods

An impl block attaches functions to a type. One that does not take self is an associated function, called as Type::name() — this is how constructors are written, since Rust has no dedicated constructor syntax. One that does take self is a method, called with a dot. 

struct Counter {
    value: u32,
}

impl Counter {
    // Associated function: no self. `Self` means `Counter` here.
    fn new() -> Self {
        Self { value: 0 }
    }

    // &mut self — needs exclusive access to change the field.
    fn increment(&mut self) {
        self.value += 1;
    }

    // &self — only reads, so many callers can share it.
    fn current(&self) -> u32 {
        self.value
    }

    // self by value — consumes the Counter and returns its contents.
    fn into_inner(self) -> u32 {
        self.value
    }
}

let mut counter = Counter::new();
counter.increment();
println!("{}", counter.current()); // 1
let final_value = counter.into_inner(); // counter is gone after this

Pattern Matching

match is Rust's switch, except that it matches on structure rather than equality, binds the pieces it finds, and refuses to compile if you miss a case. It comes from the ML family of languages, and once it clicks you will miss it everywhere else.

  • Exhaustive. Every possible value must be covered by some arm. Add a variant to an enum and the compiler immediately lists every match that now needs updating — which is what makes refactoring Rust so much less frightening than it might be.
  • No fall-through. Arms do not run into each other; no break is needed, and forgetting one cannot silently change behaviour.
  • Wildcards. _ matches anything and discards it; a bare name matches anything and binds it.
  • An expression. A match produces a value, so it can sit on the right-hand side of a let or be a function's final line.
enum Status {
    Pending,
    Active { since: u64 },
    Error(String),
}

fn describe(status: &Status) -> String {
    match status {
        Status::Pending => "waiting to start".to_string(),

        // Struct variants destructure by field name.
        Status::Active { since } => format!("running since {since}"),

        // A match guard: an extra `if` condition on the arm.
        // Guards are checked in order, so put the specific case first.
        Status::Error(msg) if msg.is_empty() =>
            "unknown error".to_string(),

        Status::Error(msg) => format!("error: {msg}"),
    }
}

Patterns worth knowing

let pair = (3, -3);

match pair {
    // Destructure a tuple, matching a literal in one position.
    (0, y) => println!("first is zero, second is {y}"),

    // Or-patterns: several alternatives in one arm.
    (1 | 2, _) => println!("first is one or two"),

    // Ranges (inclusive only, in patterns).
    (n @ 3..=9, _) => println!("first is {n}, between 3 and 9"),
    //  ^ the @ binding captures the value AND tests the pattern

    // A guard comparing two bound values.
    (x, y) if x + y == 0 => println!("they cancel out"),

    // Catch-all. Required here, because the guard above is not
    // something the compiler can prove exhaustive.
    _ => println!("something else"),
}

// Patterns work in `let` too, when they cannot fail.
struct Point { x: i32, y: i32 }
let Point { x, y } = Point { x: 1, y: 2 };
println!("{x}, {y}");

// And in function parameters and closures.
let distances: Vec<f64> = vec![(3.0, 4.0)]
    .iter()
    .map(|(dx, dy)| (dx * dx + dy * dy).sqrt())
    .collect();

// `matches!` is a compact boolean test built on the same machinery.
let status = Status::Pending;
if matches!(status, Status::Pending) {
    println!("still pending");
}
Let the exhaustiveness check work for you

It is tempting to end every match on an enum with _ => {}. Resist it. A wildcard silently absorbs any variant added later; listing the variants explicitly turns that future addition into a compile error that points at every place needing attention. Save _ for genuinely open-ended values like integers and strings.

Control Flow for Errors

Rust has no exceptions. A function that can fail says so in its return type, and the caller must deal with it — which makes error handling part of control flow rather than something layered on top.

  • Option<T> is Some(T) or None: a value that may be absent. This is Rust's replacement for null.
  • Result<T, E> is Ok(T) or Err(E): an operation that may fail, carrying a reason when it does.

Both are ordinary enums, so everything in the previous section applies to them. What makes them pleasant to use is the ? operator: 

use std::num::ParseIntError;

// The long way, spelled out.
fn parse_verbose(raw: &str) -> Result<u16, ParseIntError> {
    let port = match raw.parse::<u16>() {
        Ok(value) => value,
        Err(e) => return Err(e), // propagate
    };
    Ok(port)
}

// The same thing with `?`: on Ok it unwraps, on Err it returns early.
fn parse_port(raw: &str) -> Result<u16, String> {
    let port: u16 = raw
        .parse()
        .map_err(|_| format!("'{raw}' is not a port number"))?;

    if port == 0 {
        Err("port cannot be zero".to_string())
    } else {
        Ok(port)
    }
}

Handling the values

let maybe: Option<i32> = Some(5);

// Supply a fallback
let a = maybe.unwrap_or(0);
let b = maybe.unwrap_or_else(|| expensive());
let c = maybe.unwrap_or_default();

// Transform without unwrapping
let d = maybe.map(|n| n * 2);
let e = maybe.filter(|n| *n > 3);

// Convert between the two
let f: Result<i32, &str> =
    maybe.ok_or("was empty");

When to unwrap

unwrap() panics on None or Err and tells you nothing about why. expect("…") panics too, but with your message attached. 

// Fine: tests, prototypes, and cases
// you can prove cannot fail.
let n: i32 = "42".parse().unwrap();

// Better everywhere else: say why
// you believe it cannot fail.
let config = load_config()
    .expect("config.toml must exist");

// Best in library code: hand the
// decision back to the caller.
let config = load_config()?;
Panics are for bugs, not for failures

The dividing line is worth internalising early. A file that is missing, a network that is down, or input that is malformed are expected conditions — return a Result. An index that is out of bounds or an invariant your own code violated is a bug — panicking is correct, because continuing would produce nonsense. Result for the world's problems, panic for yours.

Asynchronous Control Flow

Everything so far runs straight through: a statement finishes before the next one starts. Async adds a fourth kind of control flow to the three loops and the branches — the ability for a function to pause in the middle, hand control back, and be resumed later exactly where it left off.

The problem it solves

Most programs spend most of their time doing nothing. A web server waits on sockets; a scraper waits on DNS and TLS; a batch job waits on a database. The traditional answer is one thread per job, and it works well — until you want ten thousand of them, at which point the stacks and the operating system's scheduling become the bottleneck rather than the work.

Async is the other answer: a small number of threads, each juggling many jobs, switching between them at the exact points where they would otherwise sit idle.

Threads (std::thread) Async tasks
Cost of one Its own stack, plus OS scheduling Roughly a struct — often a few hundred bytes, no OS involvement
Switching The kernel preempts whenever it likes Cooperative — only at an .await
Best at CPU-bound work, and a handful of long-lived jobs I/O-bound work, and thousands of concurrent waits
Needs a library? No — it is in std Yes — std has no executor
Blocking is Normal and fine A bug — see below
The rule of thumb

If your program is waiting, async pays. If it is computing, threads pay — and rayon pays even better. A CLI tool that makes four HTTP calls does not need async at all; four blocking calls on four threads is simpler and just as fast. Async earns its complexity somewhere around "hundreds of concurrent connections".

Two keywords, and one surprise

async marks a function as pausable. await marks the point where it may pause. The surprise is what async fn actually does when you call it: 

// An async fn does not return a String. It returns an anonymous type
// implementing Future<Output = Result<String, Error>>.
async fn fetch(url: &str) -> Result<String, reqwest::Error> {
    reqwest::get(url).await?.text().await
}

fn main() {
    // Calling it runs NONE of the body. No socket is opened, no DNS
    // lookup happens. All this does is build a state machine and hand
    // it to you as a value.
    let future = fetch("https://example.com");

    // `future` is dropped here. The request was never made, and the
    // compiler warns you about exactly that.
}
Futures are lazy — this is the big difference from other languages

A JavaScript Promise, a C# Task and a Python coroutine scheduled with create_task all begin running the moment they are created. A Rust Future does nothing at all until something polls it — normally by .await-ing it or handing it to the runtime.

This is why the compiler emits "unused implementer of Future that must be used" with the note "futures do nothing unless you .await or poll them". In most languages a forgotten await means the work still happens, just unordered. In Rust it means the work never happened.

You have to bring a runtime

std defines the Future trait and the async/await syntax, and stops there. There is no executor in the standard library — the same deliberate split you will find for HTTP and databases. Two runtimes matter in practice:

  • tokio — the default choice by a wide margin. Nearly every async crate you will want (reqwest, sqlx, axum) assumes it.
  • smol — small, explicit, and pleasant when you do not need the ecosystem.
Ignore tutorials that recommend async-std

async-std was for years the main alternative to Tokio, and it appears throughout older blog posts and books. It was discontinued in 2025 and now carries a RustSec advisory (RUSTSEC-2025-0052) marking it unmaintained. Its own maintainers recommend moving to smol; for ecosystem reach, use tokio. 

[dependencies]
tokio = { version = "1", features = ["macros", "rt-multi-thread", "time"] }
// #[tokio::main] is a macro that rewrites this into an ordinary
// synchronous main which starts a runtime and blocks on your async
// body. It is the bridge from the normal world into the async one.
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let body = fetch("https://www.rust-lang.org").await?;
    println!("{} bytes", body.len());
    Ok(())
}

// Roughly what it expands to:
//   fn main() -> Result<(), Box<dyn Error>> {
//       tokio::runtime::Runtime::new()?.block_on(async { ... })
//   }

Doing several things at once

Marking a function async does not make anything concurrent by itself. Concurrency comes from how you combine futures — and getting this wrong is the most common async mistake there is.

Awaiting in a row is still sequential

.await means "wait here". Three awaits in a row wait three times, one after the other — exactly like blocking code, just without tying up the thread. 

// THREE SECONDS if each request takes one. Each await must finish
// before the next line is even reached. `async` bought nothing here.
let a = fetch(url_a).await?;
let b = fetch(url_b).await?;
let c = fetch(url_c).await?;

// ONE SECOND. join! polls all three futures on this one task,
// advancing whichever is ready, and finishes when all are done.
let (a, b, c) = tokio::join!(
    fetch(url_a),
    fetch(url_b),
    fetch(url_c),
);

// try_join! is the Result-aware version: it short-circuits and
// returns the first Err instead of collecting three of them.
let (a, b, c) = tokio::try_join!(
    fetch(url_a),
    fetch(url_b),
    fetch(url_c),
)?;
The same trap wearing a loop

for url in &urls { results.push(fetch(url).await?); } is sequential too, however many URLs there are — and it is far easier to write by accident than the three-line version above. When the count is dynamic, use the bounded-concurrency pattern on the HTTP page, which keeps a fixed number of requests in flight rather than launching all of them at once.

spawn: hand the task to the runtime

join! runs its futures on the current task — concurrent, but all on one thread. tokio::spawn gives the future to the runtime, which may run it on a different thread entirely. That is the difference between concurrency and parallelism. 

// Starts running immediately, in the background. Unlike a bare
// future, a spawned task does not need you to await it to progress.
let handle = tokio::spawn(async move {
    fetch(&url).await
});

// ... get on with something else here, genuinely at the same time ...

// Two layers of failure, so two question marks:
//   the outer ? is JoinError  — the task panicked or was aborted
//   the inner ? is your error — the fetch itself failed
let body = handle.await??;

// Many tasks, collected as they finish, with a handle on each:
let mut set = tokio::task::JoinSet::new();
for url in urls {
    set.spawn(async move { fetch(&url).await });
}
while let Some(result) = set.join_next().await {
    match result {
        Ok(Ok(body)) => println!("{} bytes", body.len()),
        Ok(Err(e))   => eprintln!("request failed: {e}"),
        Err(e)       => eprintln!("task failed: {e}"),
    }
}
Why spawn demands Send + 'static

The runtime may move the task to another thread, so everything it holds across an .await must be Send; and it may outlive the function that spawned it, so it cannot borrow local variables. That is why spawned blocks are almost always async move, and why shared state gets wrapped in Arc rather than passed by reference.

select!: whichever finishes first

Where join! waits for everything, select! waits for the first branch to complete and drops the rest. It is how timeouts, shutdown signals and races are expressed. 

use tokio::time::{sleep, Duration};

tokio::select! {
    result = fetch(url) => {
        println!("finished first: {result:?}");
    }
    _ = sleep(Duration::from_secs(5)) => {
        println!("gave up waiting");
    }
    _ = shutdown_signal() => {
        println!("asked to stop");
    }
}

That timeout pattern is common enough to have its own helper:

use tokio::time::{timeout, Duration};

// Three outcomes, and the type system makes you name all three.
match timeout(Duration::from_secs(5), fetch(url)).await {
    Ok(Ok(body))  => println!("{} bytes", body.len()),
    Ok(Err(e))    => eprintln!("the request itself failed: {e}"),
    Err(_elapsed) => eprintln!("the five seconds ran out"),
}

Cancellation is just drop

This is one of the genuinely elegant parts of the design, and one of the sharpest edges. 

// A future you simply stop awaiting is a future that stops running.
// select! cancels its losing branches by dropping them — there is no
// cancellation protocol, no flag, no exception.

let handle = tokio::spawn(long_running_job());

// Stops the task at its next .await point.
handle.abort();

// Awaiting an aborted task tells you it was cancelled.
match handle.await {
    Err(e) if e.is_cancelled() => println!("aborted"),
    other => println!("{other:?}"),
}
Nothing after the await point runs

When a future is dropped, execution stops dead at its last .await. Any code after that await — including your tidy-up — never happens. 

async fn risky() {
    let lock = acquire().await;
    do_work().await;   // <- if cancelled here…
    release(lock);      // <- …this line never runs
}

The fix is the same as everywhere else in Rust: put the cleanup in a Drop implementation, which does run when the future is dropped, and let ownership handle it. This is also why library authors talk about cancellation safety — whether a future can be dropped mid-flight and retried without losing data. It is documented per-method for anything used inside select!, and worth reading before you put a method there.

The four rules that catch everyone

  1. Never block inside async. std::thread::sleep, a blocking database driver, or a long CPU loop will freeze an entire runtime worker thread and everything scheduled on it. Use tokio::time::sleep for delays, and hand genuinely blocking work to tokio::task::spawn_blocking, which has its own thread pool for exactly this. The Databases page has the same warning for a reason.
  2. Do not hold a std::sync::MutexGuard across an .await. The guard is not Send, so the whole future stops being Send, so tokio::spawn rejects it with an error message that points at the guard. Either end the borrow before awaiting — often just an extra { } block — or use tokio::sync::Mutex, which is designed to be held across yield points.
  3. Rc and RefCell do not survive a spawn either. Same reason: not Send. Reach for Arc, and Arc<Mutex<T>> when the shared thing also needs mutating.
  4. Async spreads. Only an async fn can .await, so making one function async tends to make its callers async, all the way up to main. This is the "function colouring" complaint you will see argued about online, and it is real. It is also the main reason to decide early whether a project is async rather than converting it later.
What async compiles into

The compiler rewrites an async fn body into a state machine: an enum whose variants are the stretches of code between .await points, with every local that has to survive a pause stored as a field. .await becomes "record which state I am in, and return control to the caller".

That single fact explains most of async Rust's behaviour. Futures are plain values, so you can store them, pass them and drop them. There is no stack to unwind on cancellation, so dropping really does stop the work. And a task costs about what its largest set of live locals costs — which is why a runtime can hold hundreds of thousands of them.

Two conveniences worth knowing about

  • async fn in traits — stable since Rust 1.75, so a trait can declare async fn get(&self) -> Result<String, Error> directly. One caveat: the returned future has no automatic Send bound, so for traits whose implementations get spawned across threads the async-trait crate — which boxes the future — is still widely used.
  • Async closures — stable since Rust 1.85, alongside the AsyncFn, AsyncFnMut and AsyncFnOnce traits in the prelude. async || { … } can borrow from its captures inside the async body, which the old || async { … } workaround could not.
Where to see this in use

Async stops being abstract as soon as it is doing real work. The HTTP page uses it to run hundreds of requests with a bounded number in flight, and the Databases page covers the async drivers and connection pools — including the blocking-inside-async trap from rule 1 above.
