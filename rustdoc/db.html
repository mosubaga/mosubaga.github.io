Data Access

Databases & CSV in Rust

Connecting to PostgreSQL and MySQL, running queries that cannot be injected into, and moving tabular data in and out of your program.

On this page

PostgreSQL with tokio-postgres (async) and postgres (blocking).
MySQL and MariaDB with the mysql and mysql_async crates.
SQLx — one API for both engines, with queries checked at compile time.
CSV — reading, writing, streaming huge files, and bulk-loading into a database.

How Rust Talks to a Database

Rust's standard library has no database support at all — no JDBC, no DB-API, no built-in driver. That is deliberate: database access lives in crates, which can evolve at their own pace. What you get in exchange is a set of libraries that are unusually good at pushing errors and type mismatches to compile time.

Before writing any code, pick a layer. All four of these are mature and widely used in production:

Layer Crates What you write Reach for it when…
Native driver tokio-postgres, postgres, mysql, mysql_async SQL strings plus bound parameters You want the thinnest possible layer, or need engine-specific features like Postgres COPY or LISTEN/NOTIFY.
Async toolkit sqlx SQL, optionally verified against a live schema at compile time You want one API across PostgreSQL, MySQL and SQLite, plus pooling and migrations included.
ORM / query builder diesel, sea-orm Rust expressions that compile into SQL Your schema is large and you want the type system to catch a renamed column everywhere it is used.
Embedded rusqlite SQL against a local SQLite file You need a database with no server — tests, desktop apps, CLI tools.
Not sure? Start with SQLx

If you have no strong preference, sqlx is the easiest place to begin. It speaks plain SQL — so everything you already know transfers — and it hands you a connection pool, a migration runner and optional compile-time query checking without any extra setup.

Async or blocking?

Rust has two worlds, and database crates come in both flavours. Choosing the wrong one is the most common first stumble.

  • Blocking (postgres, mysql, rusqlite): each call occupies the current thread until the database answers. Simplest to read and debug — the right default for CLI tools, batch jobs and scripts.
  • Async (tokio-postgres, mysql_async, sqlx): every call is a .await point, so one thread can keep thousands of queries in flight. The right default for web servers and anything handling many concurrent connections.
Never block inside an async task

Calling a blocking driver from inside an async fn stalls the whole runtime worker thread and can deadlock your server under load. If you must use a blocking library from async code, hand it to tokio::task::spawn_blocking, which runs it on a separate thread pool built for exactly that.

PostgreSQL

The tokio-postgres crate is a pure-Rust implementation of the PostgreSQL wire protocol — there is no libpq to install and nothing to link against. The postgres crate is a thin blocking wrapper around it, so the two share types and behaviour.

Every example below assumes this table:

CREATE TABLE products (
    id    SERIAL PRIMARY KEY,
    name  TEXT NOT NULL,
    price DOUBLE PRECISION NOT NULL
);

tokio-postgres: connect, query, read rows

[dependencies]
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
tokio-postgres = "0.7"
use tokio_postgres::{NoTls, Error};

#[tokio::main]
async fn main() -> Result<(), Error> {
    // `connect` hands back two halves: a `client` you send queries through,
    // and a `connection` future that performs the actual socket I/O.
    let (client, connection) = tokio_postgres::connect(
        "host=localhost user=app password=secret dbname=shop",
        NoTls,
    ).await?;

    // The connection must be driven on its own task or nothing will move.
    tokio::spawn(async move {
        if let Err(e) = connection.await {
            eprintln!("connection error: {e}");
        }
    });

    // $1 is a bound parameter, NOT string interpolation. The value is sent
    // separately from the SQL text, so injection is impossible.
    let rows = client
        .query(
            "SELECT id, name, price FROM products WHERE price < $1 ORDER BY price",
            &[&25.0_f64],
        )
        .await?;

    for row in &rows {
        let id: i32 = row.get("id");
        let name: String = row.get("name");
        let price: f64 = row.get("price");
        println!("{id:>4}  {name:<20} {price:>8.2}");
    }

    // INSERT / UPDATE / DELETE use `execute`, which returns the row count.
    let affected = client
        .execute(
            "INSERT INTO products (name, price) VALUES ($1, $2)",
            &[&"Mechanical Keyboard", &89.5_f64],
        )
        .await?;
    println!("inserted {affected} row(s)");

    Ok(())
}
get panics, try_get does not

row.get() panics if the column does not exist or the Rust type does not match the SQL type. In library code, or anywhere the schema might drift, use row.try_get::<_, i32>("id")? instead and handle the error.

For a single expected row use query_one; for zero-or-one use query_opt, which returns Option<Row>. Both save you writing the "exactly one result" check by hand.

postgres: the same thing, without async

If your program has no reason to be asynchronous, the blocking crate removes the runtime, the spawned connection task and every .await. 

[dependencies]
postgres = "0.19"
use postgres::{Client, NoTls, Error};

fn main() -> Result<(), Error> {
    let mut client = Client::connect(
        "host=localhost user=app password=secret dbname=shop",
        NoTls,
    )?;

    client.execute(
        "INSERT INTO products (name, price) VALUES ($1, $2)",
        &[&"Trackball", &42.0_f64],
    )?;

    for row in client.query("SELECT id, name FROM products ORDER BY id", &[])? {
        let id: i32 = row.get(0);   // by position…
        let name: String = row.get("name"); // …or by name
        println!("{id}: {name}");
    }

    Ok(())
}
Turning on TLS

NoTls means exactly what it says — fine for a local socket, wrong for a managed database over the internet. Add the postgres-native-tls or postgres-rustls companion crate and pass its connector in place of NoTls. The rest of your code does not change.

Transactions that cannot be forgotten

A Transaction owns a mutable borrow of the client, so the compiler will not let you use the client for anything else until it is finished. Better still, its Drop implementation issues a rollback — if an error propagates with ? and the transaction is never committed, the database is not left in a half applied state. 

use postgres::{Client, NoTls, Error};

fn transfer(client: &mut Client, from: i32, to: i32, amount: f64) -> Result<(), Error> {
    let mut tx = client.transaction()?;

    tx.execute(
        "UPDATE accounts SET balance = balance - $1 WHERE id = $2",
        &[&amount, &from],
    )?;
    tx.execute(
        "UPDATE accounts SET balance = balance + $1 WHERE id = $2",
        &[&amount, &to],
    )?;

    // If either statement above returned Err, `?` exits this function and
    // `tx` is dropped — which rolls back. Nothing partial is committed.
    tx.commit()
}

This is ownership doing real work: the "did you remember to roll back?" bug is not something you can write. The same pattern applies to tokio_postgres::Transaction and to sqlx::Transaction.

Mapping SQL types to Rust types

Getting a column into the wrong Rust type is the most common runtime error with these crates. The mapping is exact, not lenient:

PostgreSQL Rust Notes
SMALLINT / INT / BIGINT i16 / i32 / i64 SERIAL is an INT, so it is i32 — not u32. Postgres has no unsigned integers.
REAL / DOUBLE PRECISION f32 / f64 Straightforward.
NUMERIC / DECIMAL rust_decimal::Decimal Needs an optional feature. Do not read money as f64.
TEXT / VARCHAR String or &str &str borrows from the Row, so it cannot outlive it.
BOOLEAN bool —
TIMESTAMPTZ chrono::DateTime<Utc> Enable the with-chrono-0_4 feature.
UUID uuid::Uuid Enable the with-uuid-1 feature.
JSON / JSONB serde_json::Value Enable with-serde_json-1.
any nullable column Option<T> The single most important row in this table.
NULL is Option, always

Reading a nullable column into a plain String panics the moment a NULL arrives. Read it as Option<String> and Rust forces you to decide what an absent value means — which is the whole point of not having null in the language.

MySQL & MariaDB

The mysql crate is the established blocking client, and mysql_async is its asynchronous sibling. Both are pure Rust, both work with MariaDB, and both use ? as the parameter placeholder rather than PostgreSQL's $1.

mysql: pool, query, map into a struct

[dependencies]
mysql = "28"
use mysql::*;
use mysql::prelude::*;

#[derive(Debug)]
struct Product {
    id: i32,
    name: String,
    price: f64,
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // A Pool is cheap to clone and safe to share between threads.
    let url = "mysql://app:secret@localhost:3306/shop";
    let pool = Pool::new(url)?;
    let mut conn = pool.get_conn()?;

    // `?` placeholders; the tuple supplies the values. `exec_drop` is for
    // statements that return no rows.
    conn.exec_drop(
        "INSERT INTO products (name, price) VALUES (?, ?)",
        ("Mechanical Keyboard", 89.5_f64),
    )?;

    // exec_map turns each row tuple into whatever you like.
    // Note the trailing comma: (value,) is a one-element tuple.
    let products = conn.exec_map(
        "SELECT id, name, price FROM products WHERE price < ? ORDER BY price",
        (25.0_f64,),
        |(id, name, price)| Product { id, name, price },
    )?;

    for p in &products {
        println!("{:>4}  {:<20} {:>8.2}", p.id, p.name, p.price);
    }

    // For a single scalar, exec_first returns Option<T>.
    let total: Option<i64> = conn.exec_first("SELECT COUNT(*) FROM products", ())?;
    println!("{} products in total", total.unwrap_or(0));

    Ok(())
}
Watch the unsigned columns

Unlike PostgreSQL, MySQL does have unsigned integers. A column declared INT UNSIGNED must be read as u32, not i32, or conversion will fail at runtime. BIGINT UNSIGNED maps to u64.

mysql_async: the same shape, awaited

[dependencies]
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
mysql_async = "0.37"
use mysql_async::prelude::*;
use mysql_async::{Pool, Row};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let pool = Pool::new("mysql://app:secret@localhost:3306/shop");
    let mut conn = pool.get_conn().await?;

    let rows: Vec<(i32, String, f64)> = "SELECT id, name, price FROM products"
        .with(())
        .fetch(&mut conn)
        .await?;

    for (id, name, price) in rows {
        println!("{id:>4}  {name:<20} {price:>8.2}");
    }

    // Return the connection, then shut the pool down cleanly.
    drop(conn);
    pool.disconnect().await?;
    Ok(())
}

mysql_async deliberately mirrors the blocking crate's vocabulary (exec_drop, exec_map, exec_first), so porting between the two is mostly a matter of adding .await.

Inserting many rows at once

Executing one INSERT per row across a network is slow no matter how fast your language is. exec_batch prepares the statement once and reuses it, and wrapping the whole thing in a transaction turns thousands of round-trip commits into one. 

use mysql::*;
use mysql::prelude::*;

struct NewProduct {
    name: String,
    price: f64,
}

fn insert_all(conn: &mut PooledConn, items: &[NewProduct]) -> Result<(), Error> {
    let mut tx = conn.start_transaction(TxOpts::default())?;

    tx.exec_batch(
        "INSERT INTO products (name, price) VALUES (?, ?)",
        items.iter().map(|item| (item.name.as_str(), item.price)),
    )?;

    tx.commit()   // dropping `tx` without this would roll back
}
Order of magnitude, not percentages

Batching plus a single transaction routinely turns a multi-minute import into a few seconds. If a data load feels slow, check how many transactions you are committing before you start profiling Rust code.

SQLx: One API, Both Engines

sqlx is worth its own section because of a trick nothing else on this page does: it can connect to your database while compiling, run your query through the server's planner, and fail the build if a column name is wrong or a Rust type does not line up with the schema. Typos in SQL become compiler errors. 

[dependencies]
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
sqlx  = { version = "0.9", features = ["runtime-tokio", "tls-rustls-ring-webpki", "macros", "postgres", "mysql"] }

PostgreSQL — $1 placeholders

use sqlx::postgres::PgPoolOptions;

#[derive(Debug, sqlx::FromRow)]
struct Product {
    id: i32,
    name: String,
    price: f64,
}

#[tokio::main]
async fn main() -> Result<(), sqlx::Error> {
    // Read credentials from the environment — never hard-code them.
    let url = std::env::var("DATABASE_URL")
        .expect("set DATABASE_URL, e.g. postgres://app:secret@localhost/shop");

    let pool = PgPoolOptions::new()
        .max_connections(5)
        .connect(&url)
        .await?;

    let products = sqlx::query_as::<_, Product>(
        "SELECT id, name, price FROM products WHERE price < $1 ORDER BY price",
    )
    .bind(25.0_f64)
    .fetch_all(&pool)
    .await?;

    for p in &products {
        println!("{:>4}  {:<20} {:>8.2}", p.id, p.name, p.price);
    }

    // Writes go through `query` + `execute`.
    sqlx::query("INSERT INTO products (name, price) VALUES ($1, $2)")
        .bind("Trackball")
        .bind(42.0_f64)
        .execute(&pool)
        .await?;

    Ok(())
}

MySQL — identical, apart from the placeholders

Swap PgPoolOptions for MySqlPoolOptions and $1 for ?. Everything else — the struct, FromRow, bind, fetch_all — is unchanged. 

use sqlx::mysql::MySqlPoolOptions;

#[derive(Debug, sqlx::FromRow)]
struct Product {
    id: i32,
    name: String,
    price: f64,
}

#[tokio::main]
async fn main() -> Result<(), sqlx::Error> {
    let url = std::env::var("DATABASE_URL")
        .expect("set DATABASE_URL, e.g. mysql://app:secret@localhost/shop");

    let pool = MySqlPoolOptions::new()
        .max_connections(5)
        .connect(&url)
        .await?;

    let products = sqlx::query_as::<_, Product>(
        "SELECT id, name, price FROM products WHERE price < ? ORDER BY price",
    )
    .bind(25.0_f64)
    .fetch_all(&pool)
    .await?;

    println!("{products:#?}");
    Ok(())
}
SQL is still SQL

SQLx unifies the API, not the dialects. Placeholder syntax, RETURNING (PostgreSQL only), auto-increment syntax and date functions still differ. If you truly need one binary to target both engines, keep the SQL behind a small trait with one implementation per database.

Queries verified by the compiler

Swap the function query_as for the macro query_as! and SQLx checks the statement against a real schema during cargo build. Misspell a column, or declare price as i32 when the column is DOUBLE PRECISION, and the build fails with a pointed message. 

#[derive(Debug)]
struct Product {
    id: i32,
    name: String,
    price: f64,
}

// Checked at COMPILE time against $DATABASE_URL.
// No `.bind()` — parameters are ordinary Rust expressions, also checked.
let products = sqlx::query_as!(
    Product,
    "SELECT id, name, price FROM products WHERE price < $1 ORDER BY price",
    25.0_f64
)
.fetch_all(&pool)
.await?;

To make this work you need two things:

  1. A DATABASE_URL available at build time — put it in a .env file at the project root, which SQLx reads automatically. Add that file to .gitignore.
  2. For CI and for builds without a database, run cargo sqlx prepare (from cargo install sqlx-cli). It caches the query metadata into a .sqlx/ directory that you commit, so offline builds stay fully checked.
Migrations come in the box

sqlx migrate add create_products writes a timestamped SQL file into migrations/; sqlx migrate run applies the pending ones. You can also embed them in the binary with sqlx::migrate!().run(&pool).await?, so deploying the app and migrating the schema become one step.

Reading a result set that will not fit in memory

fetch_all allocates a Vec containing every row. For a million-row table that is exactly what you do not want. fetch returns a stream instead — rows arrive one at a time and peak memory stays flat. 

use futures::TryStreamExt; // futures = "0.3"

let mut rows = sqlx::query_as::<_, Product>("SELECT id, name, price FROM products")
    .fetch(&pool);

let mut total = 0.0;
while let Some(product) = rows.try_next().await? {
    total += product.price;
}
println!("inventory value: {total:.2}");

The same choice exists in every driver here: fetch_all versus a cursor or stream. Reach for the streaming variant whenever the row count is unbounded or comes from user input.

Writing Queries That Stay Safe

Rust's memory safety says nothing about SQL injection — that is a logic bug, not a memory bug. The good news is that every crate on this page makes the safe path the convenient one.

Never build SQL with format!

// DANGEROUS — a name of `'; DROP TABLE products; --`
// becomes part of the statement.
let sql = format!(
    "SELECT * FROM products WHERE name = '{name}'"
);
client.query(&sql, &[]).await?;

Bind parameters instead

// SAFE — the value travels in a separate protocol field
// and is never parsed as SQL.
client.query(
    "SELECT * FROM products WHERE name = $1",
    &[&name],
).await?;
  • Parameters are values, not identifiers. You cannot bind a table or column name. If one must be dynamic, match it against a fixed allow-list of known-good strings.
  • Keep credentials out of the source tree. Read a DATABASE_URL from the environment (the dotenvy crate loads a local .env in development) and take the real value from your platform's secret store in production.
  • Use a pool, and give it a ceiling. Opening a connection costs a TCP handshake, TLS and authentication. A pool amortises that and — just as importantly — caps how many connections your service can demand from the database at once.
  • Set timeouts. acquire_timeout on the pool and a statement timeout on the server turn "the app hangs forever" into a clean, loggable error.
  • Let Result do its job. Resist .unwrap() on query results outside of tests. Propagate with ? and add context with anyhow or a thiserror enum.

Working with CSV Files

CSV is the format every system can export and no two systems agree on. The csv crate handles the awkward parts — quoted fields containing commas, embedded newlines, BOMs, inconsistent line endings — and is fast enough to parse hundreds of megabytes per second. Paired with serde, a row becomes a typed struct in one line. 

[dependencies]
csv   = "1.4"
serde = { version = "1", features = ["derive"] }

Reading rows straight into structs

Given products.csv:

id,name,unit_price,in_stock
1,Mechanical Keyboard,89.50,true
2,"Cable, braided 2m",12.00,true
3,Trackball,42.00,false

Note row 2: the field is quoted because it contains a comma. Splitting on commas by hand would get this wrong — which is the reason to use a real parser. 

use serde::Deserialize;
use std::error::Error;

#[derive(Debug, Deserialize)]
struct Product {
    id: u32,
    name: String,
    // The header says `unit_price`; call the field whatever you like.
    #[serde(rename = "unit_price")]
    price: f64,
    in_stock: bool,
}

fn main() -> Result<(), Box<dyn Error>> {
    // from_path treats the first line as a header row by default.
    let mut reader = csv::Reader::from_path("products.csv")?;

    let mut in_stock_total = 0.0;

    // deserialize() yields Result<Product, csv::Error> per row, so a
    // single malformed line cannot silently corrupt your totals.
    for result in reader.deserialize() {
        let product: Product = result?;
        if product.in_stock {
            in_stock_total += product.price;
        }
        println!("{:>4}  {:<24} {:>8.2}", product.id, product.name, product.price);
    }

    println!("value in stock: {in_stock_total:.2}");
    Ok(())
}
Missing and messy fields

Declare a field as Option<f64> and an empty cell deserialises to None instead of failing. Add #[serde(default)] to fall back to the type's default, and #[serde(rename_all = "PascalCase")] on the struct when the exporter used a different naming convention throughout.

Writing CSV

Writer quotes and escapes for you — if a value contains the delimiter, a quote or a newline, the output stays valid without you thinking about it. 

use serde::Serialize;
use std::error::Error;

#[derive(Serialize)]
struct Row<'a> {
    id: u32,
    name: &'a str,
    unit_price: f64,
}

fn export() -> Result<(), Box<dyn Error>> {
    let mut writer = csv::Writer::from_path("export.csv")?;

    // The header row is derived from the struct's field names,
    // and written automatically before the first record.
    writer.serialize(Row { id: 1, name: "Mechanical Keyboard", unit_price: 89.5 })?;
    writer.serialize(Row { id: 2, name: "Cable, braided 2m", unit_price: 12.0 })?;

    // Or write raw fields without serde:
    writer.write_record(&["3", "Trackball", "42.00"])?;

    // IMPORTANT: the writer buffers. Flushing surfaces any I/O error
    // here, where you can still handle it — a silent flush on drop
    // would throw that error away.
    writer.flush()?;
    Ok(())
}

To write to standard output instead of a file — useful for a Unix-style tool that pipes into another — swap the constructor for csv::Writer::from_writer(std::io::stdout()).

Files bigger than memory

The reader is already streaming: it never loads the whole file. The remaining cost is one allocation per row, and you can remove even that by reusing a single record buffer. 

use std::error::Error;

fn sum_column(path: &str) -> Result<f64, Box<dyn Error>> {
    let mut reader = csv::Reader::from_path(path)?;

    // One buffer, reused for every row: no per-row allocation at all.
    let mut record = csv::StringRecord::new();
    let mut total = 0.0;
    let mut line = 1; // header

    while reader.read_record(&mut record)? {
        line += 1;
        // Report which line was bad rather than just "invalid float".
        total += record[2]
            .parse::<f64>()
            .map_err(|e| format!("line {line}, column 3: {e}"))?;
    }

    Ok(total)
}
Two more speed levers

Use ByteRecord instead of StringRecord to skip UTF-8 validation when the data is known-good bytes. And remember that a debug build is not a measurement — benchmark CSV work with cargo run --release.

When the file is not really CSV

Semicolon-separated European exports, tab-separated dumps, files with no header, files with a ragged number of columns — ReaderBuilder covers all of them. 

let mut reader = csv::ReaderBuilder::new()
    .delimiter(b';')        // semicolon-separated
    .has_headers(false)    // first line is data, not a header
    .flexible(true)        // tolerate rows with differing field counts
    .comment(Some(b'#'))   // skip lines beginning with #
    .trim(csv::Trim::All)  // strip surrounding whitespace from every field
    .from_path("export.tsv")?;

Two encoding notes that catch people out. First, the csv crate expects UTF-8; for a Windows-1252 or Shift-JIS file, decode it first with the encoding_rs crate. Second, spreadsheets often write a UTF-8 byte-order mark, which turns your first header into "\u{feff}id" and breaks the matching field name — strip it before parsing, or wrap the file in encoding_rs_io::DecodeReaderBytes, which removes it for you.

Loading a CSV file into a database

This is the job that ties the whole page together, and the naive version — one INSERT per line, each in its own transaction — is the classic performance trap. Both engines offer a much better route.

PostgreSQL: COPY

COPY … FROM STDIN is by far the fastest bulk-load path, and the driver exposes it as an ordinary Write sink. You can stream the file straight through: 

use postgres::{Client, NoTls};
use std::io::copy;
use std::fs::File;

fn bulk_load(client: &mut Client)
    -> Result<u64, Box<dyn std::error::Error>>
{
    let mut file = File::open("products.csv")?;

    let mut writer = client.copy_in(
        "COPY products (name, price) FROM STDIN \
          WITH (FORMAT csv, HEADER true)",
    )?;

    // Streams the file in chunks — memory stays flat.
    copy(&mut file, &mut writer)?;

    // finish() returns the number of rows the server accepted.
    Ok(writer.finish()?)
}

MySQL: parse, then batch

MySQL's LOAD DATA LOCAL INFILE is often disabled by server or client policy, so the portable approach is to parse in Rust and insert in prepared batches: 

use mysql::prelude::*;
use mysql::{PooledConn, TxOpts};
use serde::Deserialize;

#[derive(Deserialize)]
struct Row { name: String, price: f64 }

fn bulk_load(conn: &mut PooledConn)
    -> Result<(), Box<dyn std::error::Error>>
{
    let mut reader = csv::Reader::from_path("products.csv")?;
    let rows: Vec<Row> = reader
        .deserialize()
        .collect::<Result<_, _>>()?; // first error wins

    let mut tx = conn.start_transaction(TxOpts::default())?;
    tx.exec_batch(
        "INSERT INTO products (name, price) VALUES (?, ?)",
        rows.iter().map(|r| (r.name.as_str(), r.price)),
    )?;
    tx.commit()?;
    Ok(())
}
One small detail worth stealing

.collect::<Result<Vec<_>, _>>()? in the example above is a genuinely lovely piece of Rust: collecting an iterator of Results into a Result<Vec<_>> stops at the first error and returns it. One line replaces a loop, a mutable accumulator and an early return. There is more of this on the Collections & Iterators page.
