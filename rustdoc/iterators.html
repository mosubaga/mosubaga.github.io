Collections & Iterators in Rust

How vectors, slices and maps are laid out in memory — and why chaining iterator adapters costs nothing at runtime.

On this page

Picking a Collection

Most Rust programs need exactly two: Vec for a sequence and HashMap for a lookup table. Start there, and move to something else only when you can name the reason.

Type Shape Good at Reach for it when…
Vec<T> Growable contiguous array Push/pop at the end and index access, both O(1) amortised Nearly always. Contiguity makes it enormously cache-friendly.
VecDeque<T> Ring buffer O(1) push and pop at both ends Queues and sliding windows, where Vec::remove(0) would be O(n).
HashMap<K, V> Open-addressed hash table O(1) average lookup, insert and remove Key/value lookup where iteration order does not matter.
BTreeMap<K, V> B-tree O(log n) lookup, and iteration in sorted key order You need ordering, range queries, or deterministic iteration.
HashSet<T> / BTreeSet<T> The maps, without values Membership tests; union, intersection, difference You care whether something is present, not what it maps to.
BinaryHeap<T> Max-heap O(1) peek at the largest, O(log n) push and pop Priority queues and scheduling. Wrap items in Reverse for a min-heap.
String / &str UTF-8 bytes Owned and borrowed text Always, for text. Neither can be indexed by character position — see the note below.
Strings are not arrays of characters

A String is a Vec<u8> guaranteed to hold valid UTF-8. Because one character can occupy one to four bytes, s[3] does not compile at all — there is no meaningful answer. Use s.chars().nth(3) for the fourth character, s.len() for the byte length, and s.chars().count() for the character count. That the two lengths differ is a fact about text, not a quirk of Rust.

The Iterator Foundation

An iterator in Rust is any type implementing the Iterator trait. The trait is remarkably small: one associated type and one required method. 

pub trait Iterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;

    // …and around eighty provided methods, all built on next().
}

Implement next and you get map, filter, zip, sum, collect and the rest for free. Collections implement the companion IntoIterator trait, which is what a for loop actually calls: 

// What you write
for item in collection {
    println!("{item}");
}

// Roughly what the compiler expands it into
let mut iter = IntoIterator::into_iter(collection);
while let Some(item) = iter.next() {
    println!("{item}");
}
Iterators are lazy

Calling map() or filter() does no work at all. It builds a new struct that remembers the closure. Nothing runs until something calls next() — a for loop, or a consuming method like collect(), sum() or count(). This is why the compiler warns about an unused iterator: an adapter chain you never consume genuinely does nothing.

Three ways to iterate, three levels of access

This distinction accounts for a large share of early borrow-checker friction, and it is the same shared / exclusive / owned choice that governs everything else in Rust.

Call Yields What happens to the collection for loop equivalent
.iter() &T Shared borrow — read-only, still yours afterwards for x in &c
.iter_mut() &mut T Exclusive borrow — edit in place, still yours afterwards for x in &mut c
.into_iter() T Consumed — the collection is moved and gone for x in c
One arrays footnote

Since Rust 1.53, arrays implement IntoIterator by value, so for x in [1, 2, 3] and IntoIterator::into_iter(array) yield owned T values. The method call array.into_iter() kept its old reference-yielding behaviour in the 2015 and 2018 editions for compatibility, and yields owned values in the 2021 edition and later.

Why Rust's Iterators Are Different

Zero-cost abstraction Performance

Adapters are generic structs, so the compiler monomorphises them: it generates a concrete version for your exact types, then inlines the next() calls into one another. A chain of five adapters collapses into a single loop body with no closures, no virtual dispatch and no intermediate collections. The generated assembly is routinely identical to a hand-written loop — sometimes better, because the shape is easier for the optimiser to vectorise.

No bounds check to elide Performance

Indexing with v[i] compiles to a length comparison and a conditional panic on every access. An iterator does not index at all — it walks a pointer it already proved is in range, so there is no check to generate in the first place. This is why idiomatic iteration is both the safe option and the fast one, rather than a trade-off between them.

Invalidation is impossible Safety

In C++, mutating a container while iterating it is undefined behaviour. In Java it throws ConcurrentModificationException at runtime. In Python, mutating a dict during iteration raises, while mutating a list can silently skip elements. Rust rejects the whole class at compile time: the iterator holds a borrow, so the collection is frozen until that borrow ends.

Composition without cost Ergonomics

Because iterators are lazy and generic, chaining is free. There is no intermediate Vec between a filter and a map, and no reason to fuse stages by hand for performance. You can write the pipeline that reads clearest and trust the compiler to collapse it. 

let numbers = [1, 2, 3, 4, 5, 6];

// Reads as: take the even numbers, square them, add them up.
// Compiles to: one loop, no allocation, no intermediate collection.
let sum_of_even_squares: u32 = numbers
    .iter()                      // yields &u32
    .filter(|&&n| n % 2 == 0)   // closure sees &&u32; && destructures it
    .map(|&n| n * n)             // &u32 -> u32, then square
    .sum();

assert_eq!(sum_of_even_squares, 56); // 4 + 16 + 36

// `.copied()` avoids the reference-pattern noise entirely.
let same: u32 = numbers
    .iter()
    .copied()                    // &u32 -> u32 from here on
    .filter(|n| n % 2 == 0)
    .map(|n| n * n)
    .sum();

Slices, Vectors and Reallocation

Understanding the memory layout is what makes the borrow checker's complaints predictable rather than arbitrary.

Slices are fat pointers (&[T])

A slice [T] is a dynamically sized type: its length is not part of its type, so it cannot be stored on its own. You always handle it behind a reference, and that reference is two words wide — 16 bytes on a 64-bit platform:

  • Pointer — the address of the first element in the view.
  • Length — a usize count of elements.

A slice owns nothing. It is a cheap, non-copying window onto an array, a Vec, or part of either. That is why &[T] is the right parameter type for a function that just reads a sequence: it accepts all of them.

Vectors own a heap buffer (Vec<T>)

A Vec is three words stored wherever the binding lives, pointing at a heap allocation it owns:

  • Pointer — the heap buffer's address.
  • Capacity — how many elements fit before it must grow.
  • Length — how many are actually initialised.

When push hits the capacity, the vector allocates a larger buffer (typically double), moves the existing elements across, frees the old one, and updates its pointer. The cost is amortised O(1) — but every existing address into the old buffer is now invalid.

The bug this prevents

In C++ that reallocation is the classic dangling-iterator crash: you hold a pointer into a vector, the vector grows, the old buffer is freed, and your pointer now reads memory that belongs to something else. It is undefined behaviour, and it may not crash until much later.

Rust removes it at compile time. Taking a slice or starting an iteration acquires a shared borrow of the vector. While that borrow is alive, the vector is read-only — and push, remove, clear and friends all require an exclusive borrow, which the compiler will not grant. 

let mut v = vec![1, 2, 3];

let first = &v[0];      // shared borrow of v starts here
// v.push(4);          // ERROR[E0502]: cannot borrow `v` as mutable
//                    // because it is also borrowed as immutable
println!("{first}");   // borrow is last used here, so it ends here

v.push(4);              // now fine — nothing is borrowing v any more

// Reserve up front when you know the size: one allocation, no
// repeated copying as the vector grows.
let mut ready = Vec::with_capacity(1_000);
for i in 0..1_000 {
    ready.push(i);
}
Borrows end at last use, not at the closing brace

Since Rust 2018 the borrow checker has used non-lexical lifetimes: a borrow ends where it is last used, not at the end of the enclosing block. In the snippet above, moving println!("{first}") above the push would make the code compile. Many "the borrow checker is fighting me" moments are really "move that line up".

The Adapter Vocabulary

Learning the adapter names is the single highest-return investment in becoming productive with Rust. Almost every loop you were about to write already has a name.

Adapters that produce another iterator

All of these are lazy — they build a pipeline and wait.

Adapter Does
map(f) Applies f to every item.
filter(p) Keeps items where p returns true.
filter_map(f) Both at once: f returns Option, and None drops the item.
enumerate() Pairs each item with its index: (usize, T).
zip(other) Walks two iterators in lockstep; stops at the shorter one.
chain(other) Runs one iterator, then the next.
rev() Iterates backwards (needs a double-ended iterator).
take(n) / skip(n) First n items / everything after the first n.
take_while(p) / skip_while(p) The same, but bounded by a predicate rather than a count.
flatten() / flat_map(f) Flattens nested iterators into one stream.
copied() / cloned() Turns &T into T.
peekable() Adds peek() to look at the next item without consuming it.
inspect(f) Runs f on each item and passes it through — ideal for debugging a pipeline.

Consumers that end the pipeline

These call next() and produce a final value.

Consumer Produces
sum() / product() The total or the product.
count() How many items there were.
min() / max() Option<T> — None for an empty iterator.
min_by_key(f) / max_by_key(f) The same, comparing a derived key.
fold(init, f) Accumulates from a starting value — the most general consumer.
reduce(f) fold using the first item as the initial value.
any(p) / all(p) bool. Both short-circuit as soon as the answer is known.
find(p) / position(p) The first matching item / its index, as an Option.
last() / nth(n) A single item by position.
for_each(f) Nothing — runs f for its side effects.
collect() A whole new collection. See the next tab.

collect() is more flexible than it looks

collect builds any type implementing FromIterator. The target type is what decides the behaviour, which is why you often need to name it. 

use std::collections::{HashMap, HashSet, BTreeMap};

let words = ["apple", "banana", "apple", "cherry"];

// …into a Vec (the turbofish and the annotation are equivalent)
let upper: Vec<String> = words.iter().map(|w| w.to_uppercase()).collect();
let upper = words.iter().map(|w| w.to_uppercase()).collect::<Vec<_>>();

// …into a set, which deduplicates for free
let unique: HashSet<&str> = words.iter().copied().collect();
assert_eq!(unique.len(), 3);

// …into a map, from an iterator of pairs
let lengths: HashMap<&str, usize> = words
    .iter()
    .map(|w| (*w, w.len()))
    .collect();

// …into a sorted map, just by changing the target type
let sorted: BTreeMap<&str, usize> = words
    .iter()
    .map(|w| (*w, w.len()))
    .collect();

// …into a String
let joined: String = words.iter().copied().collect::<Vec<_>>().join(", ");
The trick worth remembering

An iterator of Results collects into a Result<Vec<_>, E>: it stops at the first error and returns it, or gives you the whole vector if everything succeeded. One line replaces a loop, an accumulator and an early return. The same works for Option. 

let inputs = ["1", "2", "three", "4"];

// Err on the first failure
let all: Result<Vec<i32>, _> = inputs.iter().map(|s| s.parse::<i32>()).collect();
assert!(all.is_err());

// Or skip the failures and keep what parsed
let good: Vec<i32> = inputs.iter().filter_map(|s| s.parse().ok()).collect();
assert_eq!(good, vec![1, 2, 4]);

Patterns you will use constantly

use std::collections::HashMap;

// ---- Counting occurrences with the entry API --------------------
// `entry` looks the key up once, whether or not it is present.
let text = "the quick brown fox jumps over the lazy dog the end";
let mut counts: HashMap<&str, u32> = HashMap::new();

for word in text.split_whitespace() {
    *counts.entry(word).or_insert(0) += 1;
}
assert_eq!(counts["the"], 3);

// ---- Grouping into buckets --------------------------------------
let names = ["alice", "bob", "anna", "carl"];
let mut by_initial: HashMap<char, Vec<&str>> = HashMap::new();

for name in names {
    if let Some(first) = name.chars().next() {
        by_initial.entry(first).or_default().push(name);
    }
}

// ---- Sorting ----------------------------------------------------
let mut scores = vec![("bob", 72), ("alice", 91), ("carl", 91)];

// sort_by_key is stable: equal keys keep their original order.
scores.sort_by_key(|&(_, score)| std::cmp::Reverse(score));

// sort_unstable_by is faster and allocates nothing, but may reorder
// equal elements. Prefer it when ties genuinely do not matter.
scores.sort_unstable_by(|a, b| b.1.cmp(&a.1));

// ---- Editing a Vec in place -------------------------------------
let mut values = vec![1, 2, 2, 3, 4, 5, 6];
values.retain(|&n| n % 2 == 0);   // keep only the evens
values.dedup();                    // drop consecutive duplicates

// ---- Windows and chunks over a slice ----------------------------
let readings = [10, 12, 11, 15, 14];

// Overlapping pairs, for deltas or moving averages
let deltas: Vec<i32> = readings.windows(2).map(|w| w[1] - w[0]).collect();
assert_eq!(deltas, vec![2, -1, 4, -1]);

// Non-overlapping batches, e.g. for a batched insert
for batch in readings.chunks(2) {
    println!("{batch:?}");
}

// ---- Splitting a pipeline in two --------------------------------
let (even, odd): (Vec<i32>, Vec<i32>) =
    (1..=10).partition(|n| n % 2 == 0);
When not to use an iterator chain

Iterators are not a moral obligation. A plain for loop is clearer when the body has early returns, uses ?, mutates several things at once, or is simply long. Deeply nested flat_map chains and closures that need three lines each are harder to read than the loop they replaced — and the compiler produces the same code either way. Choose the one a colleague will understand faster.

A Closer Look at Maps

HashMap and BTreeMap offer the same interface with different guarantees, and the choice usually comes down to one question: do you need order?

HashMap<K, V> BTreeMap<K, V>
Structure Open-addressed hash table (the SwissTable design, via hashbrown) B-tree — many keys per node, so far better cache locality than a binary tree
Lookup O(1) average O(log n)
Iteration order Unspecified, and deliberately varies between runs Always sorted by key
Key requirement Hash + Eq Ord
Range queries Not supported map.range("a".."m")
Why the default hasher is not the fastest one

HashMap uses SipHash 1-3 with a per-instance random seed. That is not the quickest hash available, and the choice is deliberate: it makes hash-collision denial-of-service attacks impractical, which matters when keys come from untrusted input. For internal maps with trusted keys you can swap in a faster hasher such as ahash or rustc-hash and often win a noticeable amount — but make that an informed decision rather than a default. 

use std::collections::HashMap;

let mut capitals = HashMap::new();
capitals.insert("Tonga", "Nuku'alofa");
capitals.insert("Fiji", "Suva");

// get() returns Option<&V> — no panic on a missing key.
if let Some(city) = capitals.get("Fiji") {
    println!("Fiji: {city}");
}

// Indexing with [] panics if absent — convenient in tests, risky elsewhere.
println!("{}", capitals["Tonga"]);

// Iterating by shared reference yields (&K, &V).
for (country, city) in &capitals {
    println!("The capital of {country} is {city}");
}

// Mutable iteration yields (&K, &mut V): values can change, keys cannot.
// Mutating a key would invalidate its hash and corrupt the table, so the
// type system simply does not offer it.
let mut tallies: HashMap<&str, i32> = HashMap::new();
tallies.insert("a", 1);
for (_key, value) in &mut tallies {
    *value *= 10;
}
