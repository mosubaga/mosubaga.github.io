The Wasm Sandboxing Model

WebAssembly is a portable binary instruction format designed as a compilation target for languages like Rust, C and C++. It has been supported by every major browser since 2017 and became a W3C recommendation in December 2019. Rust was among the first languages to support it well, and remains one of the very best fits: no garbage collector to ship, no runtime to bootstrap, and a type system that maps cleanly onto Wasm's own.

Wasm is not only a browser technology. The same sandbox model makes it a compelling way to run untrusted plugins inside a server process, which is why it shows up in edge platforms and plugin systems as often as in web pages.

Designed for untrusted code

Wasm assumes the module might be hostile. A module can only touch memory the host explicitly gave it, and can only call functions the host explicitly imported. There is no ambient authority: no filesystem, no sockets, no clock, unless the embedder hands one over. That makes it a genuinely useful way to run a third-party plugin you have not audited.

The linear memory model

A module's heap is a single contiguous byte array — in a browser, an ordinary ArrayBuffer the JavaScript side can see. Every pointer inside the module is just an offset into that array, and every access is bounds-checked against its length. The module never learns a real machine address and cannot reach a single byte outside its own buffer.

What the sandbox does not give you

The isolation is between the module and its host — not within the module. A C program compiled to Wasm can still overflow a buffer and corrupt its own heap; the sandbox only guarantees it cannot corrupt yours. Two consequences worth remembering: Rust's own safety guarantees are still doing real work inside the module, and a Wasm module is not automatically safe to hand secrets to — anything in its linear memory is visible to the page that hosts it.

Where it runs in production

Beyond the browser, Wasm is the execution layer for Fastly Compute and is supported by Cloudflare Workers for edge computing; Polkadot executes its runtime as Wasm and CosmWasm brings Wasm smart contracts to the Cosmos ecosystem. Standalone runtimes such as Wasmtime and Wasmer run .wasm files directly on a server, using WASI and related host APIs to grant controlled access to capabilities such as files, clocks, environment variables and, where supported, networking.

Picking the Right Target

Rust ships several WebAssembly targets, and choosing the wrong one produces confusing errors. Install the one you need with rustup target add:

Target Environment Use it for
wasm32-unknown-unknown The browser, via JavaScript Everything on this page. No operating system is assumed, so std::fs and std::net are unavailable — the host provides those through imported functions instead.
wasm32-wasip1 A WASI runtime (Wasmtime, Wasmer) Server-side and CLI Wasm, where files, environment variables and clocks do exist — but only the ones the runtime grants.
wasm32-wasip2 WASI Preview 2 runtimes The newer component-model flavour of WASI, with richer interface types.
wasm32-unknown-emscripten Emscripten toolchain Interoperating with an existing C/C++ Emscripten codebase. Rarely the right choice for new Rust projects. 
rustup target add wasm32-unknown-unknown

Rust to Wasm: a Walkthrough

Raw WebAssembly can only pass numbers across its boundary — integers and floats, nothing else. The wasm-bindgen crate closes that gap: it generates the JavaScript glue that copies strings, structs, closures and Vecs in and out of linear memory, so both sides can work with normal values.

Configure the manifest

The crate must build as a cdylib so the compiler emits a .wasm object rather than a Rust .rlib. Keeping rlib in the list as well means cargo test can still run your unit tests natively — a small thing that saves a lot of friction. 

[package]
name = "wasm_math_lib"
version = "0.1.0"
edition = "2024"

[lib]
# cdylib -> the .wasm artifact; rlib -> native `cargo test` still works
crate-type = ["cdylib", "rlib"]

[dependencies]
wasm-bindgen = "0.2"

# Optional but recommended: a much smaller release binary.
[profile.release]
opt-level = "z"       # optimise for size rather than speed
lto = true          # link-time optimisation across crates
codegen-units = 1   # slower build, smaller output
panic = "abort"    # drop the unwinding machinery
strip = true        # remove debug symbols

Write the Rust

Annotate anything you want JavaScript to see with #[wasm_bindgen]. It works on free functions, structs, their methods, and enums. 

use wasm_bindgen::prelude::*;

// A plain numeric function: the cheapest possible boundary crossing.
#[wasm_bindgen]
pub fn gcd(a: u32, b: u32) -> u32 {
    let (mut x, mut y) = (a, b);
    while y != 0 {
        let t = y;
        y = x % y;
        x = t;
    }
    x
}

// Strings are copied across the boundary — cheap for a few words,
// worth measuring if you do it in a hot loop.
#[wasm_bindgen]
pub fn shout(name: &str) -> String {
    format!("HELLO, {}!", name.to_uppercase())
}

// A struct becomes a JavaScript class with a real destructor:
// call counter.free() when done for deterministic cleanup.
#[wasm_bindgen]
pub struct Counter {
    value: i32,
}

#[wasm_bindgen]
impl Counter {
    // Exposed to JS as `new Counter(start)`
    #[wasm_bindgen(constructor)]
    pub fn new(start: i32) -> Counter {
        Counter { value: start }
    }

    pub fn increment(&mut self) {
        self.value += 1;
    }

    #[wasm_bindgen(getter)]
    pub fn value(&self) -> i32 {
        self.value
    }
}

// Returning Result<T, JsValue> makes the JS call throw on Err.
#[wasm_bindgen]
pub fn parse_port(raw: &str) -> Result<u16, JsValue> {
    raw.parse::<u16>()
        .map_err(|e| JsValue::from_str(&format!("bad port: {e}")))
}
Reaching the browser from Rust

Two companion crates complete the picture. js-sys binds JavaScript's built-ins (Array, Date, Promise, Math), and web-sys binds the Web APIs — the DOM, fetch, Canvas, WebGL, Web Audio. web-sys is enormous, so every interface sits behind a cargo feature and you enable only the handful you use.

Call it from the page

With --target web, wasm-pack emits an ES module whose default export is an async initialiser. Await it once, then call your functions like any other import. 

<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <title>Wasm Test Page</title>
</head>
<body>
    <p id="out">loading…</p>

    <script type="module">
        // The default export boots the module; the named exports are
        // your #[wasm_bindgen] items.
        import init, { gcd, shout, Counter } from './pkg/wasm_math_lib.js';

        async function run() {
            // Fetches and compiles the .wasm binary. Do this once.
            await init();

            const counter = new Counter(10);
            counter.increment();

            document.getElementById('out').textContent =
                `gcd(24, 81) = ${gcd(24, 81)} · ` +
                `${shout('ferris')} · counter = ${counter.value}`;

            // Free exported Rust objects when you know you are done with them.
            counter.free();
        }

        run();
    </script>
</body>
</html>
Prefer explicit free()

A #[wasm_bindgen] struct lives in the Wasm module's linear memory, which the JavaScript garbage collector does not manage directly. Modern wasm-bindgen can use FinalizationRegistry / weak references to clean up eventually when the host supports them, but explicit .free() is still deterministic and works everywhere. Plain functions taking and returning values have no such lifecycle concern — this applies to exported object instances and long-lived closures.

Build the package

# One-time setup
rustup target add wasm32-unknown-unknown
cargo install wasm-pack

# Build an ES-module package into ./pkg
wasm-pack build --target web --release

You end up with a pkg/ directory containing everything the page needs:

pkg/
├── wasm_math_lib.js        # ES module: init() + your exports
├── wasm_math_lib_bg.wasm   # the compiled binary
├── wasm_math_lib.d.ts      # TypeScript definitions, generated for free
└── package.json            # so it can be published to npm if you want
wasm-pack optimises for you

A release build runs wasm-opt (from Binaryen) over the output automatically, which typically cuts a further 15–30% off the file. You can pass your own flags via [package.metadata.wasm-pack.profile.release] in Cargo.toml. To find out what is actually taking up space, run twiggy top pkg/*.wasm.

Five Ways to Bind Wasm into a Static Site

"Static site" means no application server: just files on a CDN. Wasm fits that model perfectly — the .wasm file is an ordinary static asset the browser fetches like an image. What differs between the approaches is how the JavaScript side finds and boots it.

Here they are from lightest to heaviest. All five produce a folder you can drop on any static host.

# Approach Build command Best for
1 ES module wasm-pack build --target web Adding Rust to a hand-written HTML page. The default recommendation.
2 Classic script tag wasm-pack build --target no-modules Legacy pages, CMS templates, anywhere type="module" is not an option.
3 Trunk trunk build --release A whole application written in Rust (Yew, Leptos, Dioxus, Sycamore).
4 JS bundler wasm-pack build --target bundler Dropping a Rust module into an existing Vite / webpack / Rollup app.
5 No bindgen at all cargo build --target wasm32-unknown-unknown Tiny numeric kernels, and understanding what the tools above are doing.

1. ES module — --target web

The browser loads the generated JavaScript as a native ES module; that module fetches and instantiates the .wasm next to it. No bundler, no npm, no build step beyond wasm-pack itself. 

wasm-pack build --target web --release --out-dir site/pkg
site/                 <- upload this whole folder
├── index.html
└── pkg/
    ├── wasm_math_lib.js
    └── wasm_math_lib_bg.wasm
<script type="module">
    import init, { gcd } from './pkg/wasm_math_lib.js';
    await init();          // top-level await works in modules
    console.log(gcd(24, 81));
</script>
  • Works on every static host with zero configuration.
  • Generates TypeScript definitions alongside the JavaScript.
  • Loads lazily — the Wasm is only fetched when the module is imported.

The one constraint is that ES modules require an http:// or https:// origin. Opening the file directly from disk will not work; see the deployment checklist below.

2. Classic script tag — --target no-modules

Sometimes you cannot use type="module": a CMS that strips the attribute, a legacy template, or a page that must work in an unusual embedding. This target emits a plain script that attaches a global wasm_bindgen object. 

wasm-pack build --target no-modules --release --out-dir site/pkg
<script src="./pkg/wasm_math_lib.js"></script>
<script>
    // Exports hang off the global object the script above created.
    const { gcd } = wasm_bindgen;

    async function run() {
        await wasm_bindgen();   // finds the .wasm next to the script
        console.log(gcd(24, 81));
    }
    run();
</script>
Trade-offs

It pollutes the global namespace, does not support inline JS snippets, and is awkward inside workers. Use it when option 1 genuinely is not available — otherwise prefer the ES module. Note that this target still fetches the .wasm over the network, so it also needs a real HTTP server.

3. Trunk — a build tool for whole Rust web apps

Trunk inverts the usual relationship: your index.html is the build manifest. Trunk reads it, finds the link tags, builds the Rust, hashes the outputs, rewrites the references and writes a finished static site to dist/. It is the standard tool for Yew, Leptos, Dioxus and Sycamore apps, but it works just as well for a plain wasm-bindgen crate. 

cargo install trunk
rustup target add wasm32-unknown-unknown

trunk serve            # dev server on :8080, rebuilds and reloads on save
trunk build --release  # production output in dist/

The source index.html at the crate root:

<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <title>My Rust App</title>

    <!-- Trunk builds this crate to Wasm and injects the loader -->
    <link data-trunk rel="rust">

    <!-- It will also compile Sass and copy static assets -->
    <link data-trunk rel="scss" href="styles/main.scss">
    <link data-trunk rel="copy-dir" href="assets">
</head>
<body></body>
</html>
  • Content-hashed filenames, so you can cache aggressively and never serve a stale binary.
  • A live-reloading dev server that already sets the right MIME types.
  • --public-url /repo-name/ fixes asset paths for a GitHub Pages subdirectory in one flag.
  • Runs wasm-opt on release builds.

4. Through a JavaScript bundler — --target bundler

If your site is already built by Vite, webpack or Rollup, this target produces a package the bundler treats as an ordinary dependency. Import it and the bundler handles fetching, instantiation and asset fingerprinting for you — the Wasm becomes just another hashed file in your output directory. 

wasm-pack build --target bundler --release
// With Vite, add the vite-plugin-wasm plugin, then:
import { gcd, shout } from './pkg/wasm_math_lib.js';

// No explicit init() — the bundler wires up instantiation.
console.log(gcd(24, 81));

The output is a normal npm package, so a shared Rust library can be published to npm and consumed by several front-ends. Static hosting still applies: the bundler's dist/ is a folder of files with no server behind it.

5. No wasm-bindgen at all

You do not actually need any tooling. cargo can emit a .wasm file on its own, and the browser's WebAssembly API can load it. The catch is the one mentioned at the top of this page: only numbers cross the boundary. No strings, no structs, no automatic memory management. 

// src/lib.rs — no dependencies whatsoever

// `no_mangle` keeps the symbol name intact; `extern "C"` gives it
// the calling convention Wasm exports use.
#[unsafe(no_mangle)]
pub extern "C" fn gcd(a: u32, b: u32) -> u32 {
    let (mut x, mut y) = (a, b);
    while y != 0 {
        let t = y;
        y = x % y;
        x = t;
    }
    x
}
[lib]
crate-type = ["cdylib"]
cargo build --release --target wasm32-unknown-unknown
cp target/wasm32-unknown-unknown/release/tiny.wasm site/
<script type="module">
    // instantiateStreaming compiles while the file is still downloading,
    // but it REQUIRES the Content-Type: application/wasm header.
    const { instance } = await WebAssembly.instantiateStreaming(
        fetch('./tiny.wasm')
    );

    console.log(instance.exports.gcd(24, 81)); // 3
</script>
Why this is worth trying once

The resulting file can be a couple of kilobytes, and building it makes the rest obvious: wasm-bindgen's entire job is writing the glue that copies non-numeric data in and out of instance.exports.memory. Once you have done it by hand, the generated JavaScript stops looking like magic.

A middle path also exists: build with plain cargo, then run the wasm-bindgen CLI over the artifact yourself (cargo install wasm-bindgen-cli, then wasm-bindgen --target web --out-dir pkg target/…/app.wasm). That is exactly what wasm-pack automates, and it is useful when you need to slot the step into an existing build pipeline.

Hosting the Result

Once built, a Rust Wasm site is just files. Everything that can go wrong from here is a server configuration issue, and there are only a few of them.

You cannot open it with file://

Double-clicking index.html will fail every time. ES modules are blocked by the same-origin policy on file://, and fetch cannot read local files either. You need an HTTP server even for local testing — which is a five-second problem, not a real one: 

# Any one of these, from the folder you want to serve
python3 -m http.server 8080

npx serve .

cargo install miniserve && miniserve . --index index.html

trunk serve   # if you are using Trunk

The MIME type

WebAssembly.instantiateStreaming refuses to compile a response that is not served as Content-Type: application/wasm. Most modern hosts and Python 3.10+ already do this correctly; older Apache and nginx installations may not. If you see an error about an "incorrect response MIME type", this is why.

nginx

types {
    application/wasm  wasm;
}

# Compresses well — often 2-4x smaller
gzip_types application/wasm;

Apache (.htaccess)

AddType application/wasm .wasm

<IfModule mod_deflate.c>
    AddOutputFilterByType DEFLATE application/wasm
</IfModule>

As a fallback that works regardless of headers, use WebAssembly.instantiate(await (await fetch(url)).arrayBuffer()). It buffers the whole file before compiling — slightly slower to start, but immune to a misconfigured MIME type.

Platform notes

Host What to know
GitHub Pages Serves .wasm correctly. Two gotchas: the site lives under /repo-name/, so build with trunk build --release --public-url /repo-name/ or use relative paths throughout; and add an empty .nojekyll file so Jekyll does not discard files and folders whose names begin with an underscore.
Netlify / Vercel Correct MIME type out of the box. Point the build command at trunk build --release or wasm-pack build --target web and publish dist/. Extra headers go in _headers or vercel.json.
Cloudflare Pages Works as-is, with Brotli compression applied automatically — usually the smallest over-the-wire size of the options here.
S3 + CloudFront S3 guesses application/octet-stream for unknown extensions, so set the type explicitly on upload: aws s3 cp app.wasm s3://bucket/ --content-type application/wasm.

Caching and load time

  • Fingerprint the filename. Trunk and JS bundlers do this automatically. With plain wasm-pack, use --out-name app-v3 or add a query string, then serve with Cache-Control: public, max-age=31536000, immutable.
  • Always compress. Wasm is a binary format that gzips and brotlis extremely well. Serving it uncompressed can easily triple the download.
  • Preload the binary. <link rel="preload" href="app_bg.wasm" as="fetch" crossorigin> starts the download in parallel with the JavaScript instead of after it.
  • Show something first. Instantiation is fast but not instant. Render static HTML, then swap in the Wasm-driven content once init() resolves — the same reasoning as any other progressive-enhancement decision.
  • Keep it small. The release profile from the walkthrough above, wasm-opt, and avoiding heavyweight dependencies matter far more than any micro-optimisation inside your Rust.
If you need threads

Wasm threads use SharedArrayBuffer, which browsers only expose to cross-origin isolated pages. That means serving two extra headers — Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp — which some static hosts do not let you set, and which will break embedded third-party content. Single-threaded Wasm needs none of this, so only take it on when you have measured that you need it.

Thinking About the Boundary

The most common disappointment with Rust in the browser is a rewrite that turns out no faster than the JavaScript it replaced. Almost always, the cause is the boundary rather than the Rust.

  • Numbers are free; everything else is copied. Passing an f64 is a machine instruction. Passing a String allocates in linear memory, copies the bytes, and copies them back out again. Calling a Rust function a million times in a JavaScript loop pays that cost a million times.
  • Move the loop into Rust. Instead of calling process(pixel) per pixel, pass the whole buffer once and return the whole result. One crossing beats a million.
  • Share the buffer instead of copying it. For large numeric data, hand JavaScript a view onto the module's memory (Uint8Array over instance.exports.memory.buffer at the right offset) so both sides read the same bytes. Remember that growing the Wasm heap detaches existing views — re-create them after any allocation.
  • Play to Wasm's strengths. It wins decisively on sustained numeric work: image and audio processing, compression, parsing, physics, cryptography, simulation. It rarely wins on DOM manipulation, because every DOM call goes back through JavaScript anyway.
Measure, then decide

Build the JavaScript version first and profile it. If the hot spot is a self-contained numeric loop, Rust will likely make it several times faster. If the time is going on DOM updates or network waits, Wasm will not help — and you will have added a build step for nothing.
