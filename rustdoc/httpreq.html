HTTP Requests in Rust

From a hand-written request over a raw socket to a pooled, typed, concurrent API client — and every useful step in between.

On this page

What std actually gives you — and why every real project reaches for a crate.
reqwest for async work and ureq when you want no runtime at all.
Turning JSON responses into typed structs, and typed structs into request bodies.
Timeouts, retries, error handling and running hundreds of requests at once.

There Is No HTTP in the Standard Library

Rust's standard library stops at TCP. std::net::TcpStream gives you a byte pipe; everything above it — request framing, headers, chunked transfer encoding, redirects, compression, TLS, connection pooling, HTTP/2 — lives in crates.

That surprises people arriving from Python or Go. The reasoning is the same as for databases: HTTP is a large, fast-moving target, and pinning an implementation to the language's six-week release train would freeze it. Instead the ecosystem settled on a shared foundation — the http crate for types, hyper for the protocol — that almost every client and server is built on, so they interoperate cleanly.

It is still worth writing one request by hand, once. HTTP/1.1 is a text protocol, and seeing it makes every library that follows less mysterious: 

use std::io::{Read, Write};
use std::net::TcpStream;

fn main() -> std::io::Result<()> {
    // Port 80 — plain HTTP. Anything with TLS would need a crate here.
    let mut stream = TcpStream::connect("example.com:80")?;

    // Every line ends with CRLF, and a blank line terminates the head.
    // HTTP/1.1 requires Host; `Connection: close` tells the server to
    // hang up when done, so read_to_string knows where the body ends.
    let request = "GET / HTTP/1.1\r\n\
                   Host: example.com\r\n\
                   Connection: close\r\n\
                   \r\n";

    stream.write_all(request.as_bytes())?;

    let mut response = String::new();
    stream.read_to_string(&mut response)?;

    for line in response.lines().take(8) {
        println!("{line}");
    }
    Ok(())
}
Read it, then never ship it

The snippet above has no TLS, no redirect handling, no chunked-encoding support, no timeout and no protection against a response large enough to exhaust memory. It is a teaching aid. Real code uses a client crate — and so does every example below.

Choosing a Client

Three crates cover essentially every case:

Crate Style Strengths Choose it when…
reqwest Async (with an optional blocking API) Batteries included: JSON, cookies, redirects, proxies, gzip/brotli, HTTP/2, multipart, connection pooling. Also compiles to WebAssembly. Almost always — especially in anything already using Tokio.
ureq Blocking only No async runtime, few dependencies, fast to compile, small binaries. CLI tools, build scripts and small utilities where pulling in Tokio would be the largest thing in the project.
hyper Low-level async The protocol implementation that reqwest itself is built on. Total control over connections and bodies. You are writing a proxy, a load balancer, or your own client library.
The one-line decision rule

Does your program already have an async runtime, or will it make more than a handful of requests at a time? Use reqwest. Otherwise use ureq and enjoy the shorter compile times. You can switch later; the shapes are very similar.

Making Requests with reqwest

[dependencies]
tokio   = { version = "1", features = ["macros", "rt-multi-thread", "fs", "io-util", "time"] }
reqwest = { version = "0.13", features = ["json", "query", "form", "stream"] }
serde   = { version = "1", features = ["derive"] }
futures = "0.3"

reqwest keeps most conveniences behind feature flags so a project that only needs plain bodies does not pay for JSON, forms or multipart. TLS via rustls is on by default, so https:// works out of the box with nothing to install on the host.

The shortest thing that works

#[tokio::main]
async fn main() -> Result<(), reqwest::Error> {
    let body = reqwest::get("https://www.rust-lang.org")
        .await?   // 1. connect, send, and receive the response HEAD
        .text()
        .await?;  // 2. read the BODY to completion

    println!("{} bytes", body.len());
    Ok(())
}
Why two .awaits?

The first resolves once the status line and headers have arrived; the body may still be streaming in. That split is what lets you check the status, inspect a Content-Length, or abandon a 404 without downloading its body. It is not ceremony — it is a genuinely useful place to make a decision.

Checking what came back

A 404 or a 500 is a perfectly successful HTTP exchange, so send() returns Ok for both. Deciding whether the status counts as a failure is your call: 

let response = client.get(url).send().await?;

println!("status: {}", response.status());          // e.g. 200 OK
println!("type:   {:?}", response.headers().get("content-type"));
println!("length: {:?}", response.content_length());

match response.status().as_u16() {
    200..=299 => println!("success"),
    429      => println!("rate limited — back off and retry"),
    404      => println!("not found"),
    _        => println!("unexpected status"),
}

// Or, to turn any 4xx/5xx straight into an Err and use `?`:
let response = client.get(url).send().await?.error_for_status()?;

JSON in, typed structs out

This is where Rust starts to feel like an advantage rather than a cost. Describe the shape you expect as a struct, and serde validates the response as it parses. A field that changed type upstream becomes a clear error at the boundary, not a mysterious undefined three modules later. 

use serde::Deserialize;
use std::time::Duration;

#[derive(Debug, Deserialize)]
struct CrateInfo {
    name: String,
    max_stable_version: String,
    downloads: u64,
    // Fields the API may omit go in an Option.
    description: Option<String>,
}

#[derive(Debug, Deserialize)]
struct CrateResponse {
    // `crate` is a Rust keyword, so rename the field.
    // (The alternative is the raw identifier `r#crate`.)
    #[serde(rename = "crate")]
    krate: CrateInfo,
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = reqwest::Client::builder()
        // Many APIs reject anonymous clients. Identify yourself.
        .user_agent("rust-intro-example/0.1 (you@example.com)")
        .timeout(Duration::from_secs(10))
        .build()?;

    let info: CrateResponse = client
        .get("https://crates.io/api/v1/crates/serde")
        .send()
        .await?
        .error_for_status()?  // 4xx / 5xx become Err here
        .json()
        .await?;         // body -> CrateResponse, validated by serde

    println!("{} v{} — {} downloads",
        info.krate.name, info.krate.max_stable_version, info.krate.downloads);
    Ok(())
}
You only declare what you use

serde ignores JSON fields your struct does not mention, so a 60-field API response needs a three-field struct if that is all you care about. When the shape is genuinely unknown, deserialize into serde_json::Value and explore — then write the struct once you know. The JSON & Text page covers serde's attributes, enum representations and error reporting in full.

Sending data

The builder handles the boring parts: .json() serialises the value and sets Content-Type: application/json; .query() encodes and appends parameters without you touching a URL string. 

use serde::{Deserialize, Serialize};

#[derive(Serialize)]
struct NewIssue<'a> {
    title: &'a str,
    body: &'a str,
    labels: Vec<&'a str>,
}

#[derive(Deserialize)]
struct CreatedIssue {
    number: u64,
    html_url: String,
}

let created: CreatedIssue = client
    .post("https://api.example.com/repos/acme/widget/issues")
    .bearer_auth(&token)                    // Authorization: Bearer …
    .header("X-Request-Id", request_id)
    .json(&NewIssue {
        title: "Borrow checker ate my homework",
        body: "Steps to reproduce…",
        labels: vec!["bug"],
    })
    .send()
    .await?
    .error_for_status()?
    .json()
    .await?;

println!("opened #{} at {}", created.number, created.html_url);

Other body types, all built the same way:

// Query string: ?q=rust&per_page=20   (needs the "query" feature)
client.get(url).query(&[("q", "rust"), ("per_page", "20")])

// Form encoding                        (needs the "form" feature)
client.post(url).form(&[("user", "ferris"), ("remember", "1")])

// Plain text or raw bytes              (no extra feature)
client.put(url).body("a plain string body")
client.put(url).body(vec![0u8, 1, 2, 3])

// Basic auth (password is an Option, because some schemes omit it)
client.get(url).basic_auth("ferris", Some("hunter2"))
Keep secrets out of the binary

A token written as a string literal ends up verbatim inside your compiled executable and in your git history. Read it from the environment with std::env::var("API_TOKEN")?, and make sure your error and debug logging never prints the header back out.

Build one Client and keep it

This is the single most common performance mistake with reqwest. A Client owns a connection pool and the configuration used to build new connections. Constructing one per request throws the pool away and often pays for a fresh TCP and TLS handshake every time — more expensive than the request itself. 

// WRONG — a new pool, and a new TLS handshake, for every call
async fn fetch(url: &str) -> Result<String, reqwest::Error> {
    reqwest::Client::new().get(url).send().await?.text().await
}

// RIGHT — build once, share everywhere. Client is internally
// reference-counted, so `.clone()` is cheap and shares the pool.
async fn fetch(client: &reqwest::Client, url: &str) -> Result<String, reqwest::Error> {
    client.get(url).send().await?.text().await
}

A client configured the way most production code wants it:

use std::time::Duration;

let client = reqwest::Client::builder()
    .user_agent(concat!(env!("CARGO_PKG_NAME"), "/", env!("CARGO_PKG_VERSION")))
    .timeout(Duration::from_secs(30))            // whole request, including body
    .connect_timeout(Duration::from_secs(5))      // just the TCP + TLS handshake
    .pool_idle_timeout(Duration::from_secs(90))
    .redirect(reqwest::redirect::Policy::limited(5))
    .build()?;
Where to keep it

In a web service, put the Client in your shared application state and hand out clones. In a CLI, build it in main and pass a &Client down. Reach for a global OnceLock<Client> only when threading the parameter through would be genuinely painful.

Downloading a large file

.bytes() and .text() buffer the entire body in memory. For a file of unknown size that is a denial-of-service waiting to happen. Read it chunk by chunk instead and memory stays flat regardless of how big the download is: 

use tokio::io::AsyncWriteExt;

async fn download(client: &reqwest::Client, url: &str, path: &str)
    -> Result<u64, Box<dyn std::error::Error>>
{
    let mut response = client.get(url).send().await?.error_for_status()?;

    // Content-Length is a hint, not a promise — servers may omit it.
    let expected = response.content_length();
    let mut file = tokio::fs::File::create(path).await?;
    let mut written = 0u64;

    // chunk() yields the next piece as it arrives, None at the end.
    while let Some(chunk) = response.chunk().await? {
        file.write_all(&chunk).await?;
        written += chunk.len() as u64;

        if let Some(total) = expected {
            print!("\r{:.1}%", written as f64 / total as f64 * 100.0);
        }
    }

    file.flush().await?;
    Ok(written)
}

If you would rather work with the body as a Stream — to compose it with other iterator-like adapters — enable the stream feature and use response.bytes_stream() instead.

ureq: HTTP Without a Runtime

Sometimes async is simply not worth it. A build script, a one-shot CLI, a cron job — these make a handful of requests and then exit. ureq is blocking, has a small dependency tree and compiles quickly, while still bringing TLS, redirects, gzip and connection pooling. 

[dependencies]
ureq  = { version = "3", features = ["json"] }
serde = { version = "1", features = ["derive"] }
use serde::{Deserialize, Serialize};

#[derive(Deserialize)]
struct Status { ok: bool, version: String }

#[derive(Serialize)]
struct Ping { from: String }

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // No runtime, no .await — the call simply blocks until it finishes.
    let text: String = ureq::get("https://www.rust-lang.org")
        .header("Accept", "text/html")
        .call()?
        .body_mut()
        .read_to_string()?;
    println!("{} bytes", text.len());

    // POST some JSON and deserialize the reply in the same expression.
    let status: Status = ureq::post("https://api.example.com/ping")
        .send_json(&Ping { from: "ferris".into() })?
        .body_mut()
        .read_json::<Status>()?;

    println!("ok={} version={}", status.ok, status.version);
    Ok(())
}
Reuse an Agent

The free functions ureq::get / ureq::post are conveniences. For repeated calls build a ureq::Agent — the direct equivalent of a reqwest::Client, holding the connection pool and optional cookie store — and call methods on that instead.

Two differences from reqwest worth noting

Status codes are errors here. Unlike reqwest, ureq treats 4xx and 5xx as Err(Error::StatusCode) by default, so ? already covers them and you do not need an error_for_status() step. If you would rather inspect the status yourself, set http_status_as_error(false) on the agent's config.

Bodies are capped. read_to_string() and read_to_vec() stop at 10 MB by default, so a hostile or misbehaving server cannot exhaust your memory. Raise it deliberately with .with_config().limit(n) when you know you need to.

Many Requests at Once

Fetching a hundred URLs one after another spends nearly all of its time waiting on the network. Async Rust turns that wait into throughput, and because the ownership rules still apply, the concurrent version is no harder to get right than the sequential one.

The naive fix — spawning all hundred at once — will get you rate-limited or will exhaust file descriptors. buffer_unordered keeps a fixed number in flight and starts the next as each one finishes: 

use futures::stream::{self, StreamExt}; // futures = "0.3"

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = reqwest::Client::new();
    let urls = vec![
        "https://crates.io/api/v1/crates/serde",
        "https://crates.io/api/v1/crates/tokio",
        "https://crates.io/api/v1/crates/reqwest",
    ];

    let results = stream::iter(urls)
        .map(|url| {
            // Cloning a Client is cheap: it shares the same pool.
            let client = client.clone();
            async move {
                let body = client.get(url).send().await?.text().await?;
                Ok::<_, reqwest::Error>((url, body.len()))
            }
        })
        .buffer_unordered(8) // at most 8 requests in flight at any moment
        .collect::<Vec<_>>()
        .await;

    // Each result is handled individually — one failure does not lose the rest.
    for result in results {
        match result {
            Ok((url, len)) => println!("{len:>8} bytes  {url}"),
            Err(e)         => eprintln!("failed: {e}"),
        }
    }
    Ok(())
}
Two smaller patterns worth knowing

For a fixed set of different requests, tokio::try_join!(a, b, c) runs them together and gives you a tuple of results — perfect for a page that needs three API calls before it can render. And when you want each request to be cancellable or to outlive the current function, tokio::task::JoinSet gives you a handle per task.

Making It Reliable

Networks fail. Rust will not let you forget that a request can fail — send() returns a Result — but it cannot decide what "failure" means for your program. A few habits cover almost everything:

  • Always set a timeout. The default in most clients is "wait forever", which turns one unresponsive server into a hung process. Set both a connect timeout and a total timeout.
  • Retry only what is safe to retry. GET, HEAD and PUT are idempotent; retrying a POST may create the same order twice. Retry on connection errors, timeouts, 429 and 5xx — never on 4xx, which will fail identically forever.
  • Back off exponentially, with jitter. A tight retry loop is how a brief blip becomes an outage. Double the delay each attempt and add a small random offset so a fleet of clients does not synchronise.
  • Respect Retry-After. When a server sends that header with a 429 or 503, it is telling you exactly how long to wait.
  • Distinguish the failure kinds. reqwest::Error answers is_timeout(), is_connect(), is_decode() and is_status() so you can react differently to "the server is down" and "the JSON did not match my struct".
use std::time::Duration;
use tokio::time::sleep;

async fn get_with_retry(client: &reqwest::Client, url: &str, attempts: u32)
    -> Result<reqwest::Response, reqwest::Error>
{
    let mut delay = Duration::from_millis(200);

    for attempt in 1..=attempts {
        match client.get(url).send().await {
            // Success, or a client error that retrying cannot fix.
            Ok(response) if response.status().is_success()
                || response.status().is_client_error() => return Ok(response),

            // A 5xx, or a transport failure: worth another go.
            Ok(_) if attempt < attempts => {}
            Err(e) if attempt < attempts && (e.is_timeout() || e.is_connect()) => {}

            // Out of attempts — hand the last outcome back to the caller.
            Ok(response) => return Ok(response),
            Err(e) => return Err(e),
        }

        sleep(delay).await;
        delay *= 2; // add a little randomness here in production
    }

    unreachable!("loop always returns on the final attempt")
}
Or let a crate do it

Retry policies are a solved problem. reqwest-middleware together with reqwest-retry adds backoff to an existing client without touching your call sites, and backon wraps any fallible async operation in a retry strategy. Write the loop once to understand it, then use a library.

The Other Direction: Answering Requests

Everything above is about being an HTTP client. Serving HTTP in Rust is just as approachable — axum is built on the same hyper and tokio foundations, so the two halves of a system share types and a runtime. 

[dependencies]
axum  = "0.8"
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
serde = { version = "1", features = ["derive"] }
use axum::{extract::Path, routing::get, Json, Router};
use serde::Serialize;

#[derive(Serialize)]
struct Greeting {
    message: String,
}

// A handler is an ordinary async fn. Its parameters are "extractors":
// axum pulls them out of the request and rejects it if they do not fit.
async fn greet(Path(name): Path<String>) -> Json<Greeting> {
    Json(Greeting { message: format!("Hello, {name}!") })
}

#[tokio::main]
async fn main() {
    let app = Router::new()
        .route("/", get(|| async { "Hello from Rust" }))
        .route("/hello/{name}", get(greet));

    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await.unwrap();
    println!("listening on http://{}", listener.local_addr().unwrap());

    axum::serve(listener, app).await.unwrap();
}

Run it with cargo run and visit http://localhost:3000/hello/ferris. That is a complete, production-capable JSON server in under thirty lines — and the same Serialize derive that built the request bodies earlier on this page is building the response here.
