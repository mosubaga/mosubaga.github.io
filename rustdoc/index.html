Introducing Rust

Rust is a general-purpose systems programming language. It began in 2006 as a personal project by Graydon Hoare, an engineer at Mozilla; Mozilla began sponsoring the work in 2009 and announced it publicly in 2010. After a long period of rapid change, the language reached its first stable release, Rust 1.0, in May 2015. Since 2021 it has been stewarded by the independent Rust Foundation, whose founding members included AWS, Google, Huawei, Microsoft and Mozilla.

Rust has topped Stack Overflow's "most loved" (now "most admired") language ranking in the annual developer survey every year from 2016 through 2025 — ten years running, with 72% admiration in 2025. It is used in production at Amazon Web Services, Google, Cloudflare, Microsoft, Meta and Discord. The Linux kernel has had experimental Rust support since version 6.1, and Windows 11 24H2 includes a Rust implementation of GDI regions in win32kbase_rs.sys as Microsoft expands Rust support for kernel and driver work.

At its core, Rust is designed to balance three goals that have historically competed with one another: safety, productivity and control. It grants developers the performance and direct machine access of a low-level language like C or C++, while keeping the safety guarantees, expressive type system and pleasant tooling associated with high-level languages.

A stable, predictable language

A new stable Rust version ships every six weeks, and the project takes backwards compatibility seriously: code that compiled on Rust 1.0 is still expected to compile today. Occasional opt-in-only changes are grouped into editions — 2015, 2018, 2021 and 2024 — which you select per crate in Cargo.toml. Crates on different editions interoperate freely, so upgrading is never all-or-nothing.

How Rust is Different

If you are coming from JavaScript, Python, Go or Java, Rust introduces a handful of genuine paradigm shifts in how software manages memory and correctness:

No Garbage Collection

Go, Java, C# and JavaScript rely on a runtime engine and a garbage collector to reclaim memory, which costs both throughput and predictability — a collection pause can arrive at any moment. Rust compiles straight to native machine code and inserts the deallocation itself, at exactly the point where the compiler can prove the value is no longer needed. There is no collector and no virtual machine; the standard runtime support is small and mostly covers startup, panics, unwinding when enabled, and platform glue.

The Borrow Checker

Rust enforces memory safety at compile time using a static analysis pass called the borrow checker. By applying strict ownership rules — every value has a single owner, and no reference may outlive the data it points into — whole categories of bug disappear before the program ever runs: use-after-free, double-free, dangling pointers, null dereferences and data races.

Traits, Not Inheritance

Rust has no class inheritance. It models data with structs and enums, and shared behaviour with traits — closer to interfaces or type classes than to base classes. Traits can carry default method bodies and can require other traits, so you get reuse without the fragile deep hierarchies that inheritance tends to grow.

Immutability by Default

Every binding in Rust is immutable unless you say otherwise. Opting in with the mut keyword is a deliberate, visible act, so a reader can tell at a glance which parts of a function change state. This single default removes a surprising amount of accidental-mutation debugging.

An honest footnote about unsafe

Those guarantees apply to safe Rust, which is what you write almost all of the time. Rust also has an unsafe escape hatch for the handful of operations the compiler cannot verify — dereferencing a raw pointer, calling into C, or implementing a data structure the borrow checker cannot express. Inside an unsafe block the burden of proof moves to you. The value of the design is that unsafe code is rare, explicit and greppable, so a security review has a small surface to inspect rather than an entire codebase.

The One Concept: Ownership

Almost every "why won't this compile?" moment in your first weeks with Rust traces back to these rules. Learn them properly now and the rest of the language falls into place quickly.

The three ownership rules

  1. Each value in Rust has an owner.
  2. There can be only one owner at a time.
  3. When the owner goes out of scope, the value is dropped (its memory is freed, its files are closed, its locks are released).

Rule 3 is why Rust needs no garbage collector: the compiler already knows the exact line where each value dies, so it can emit the cleanup call itself.

The two borrowing rules

  1. At any given time you may have either one mutable reference (&mut T) or any number of shared references (&T) — never both.
  2. References must always be valid: a reference can never outlive the data it points to.

Rule 1 is the same rule that eliminates data races between threads. Single-threaded aliasing bugs and multi-threaded races turn out to be the same problem, so one check fixes both.

Here is all of it in fifteen lines:

fn main() {
    let greeting = String::from("hello");   // `greeting` owns the heap buffer

    let length = measure(&greeting);          // lend it out: a shared borrow
    println!("{greeting} is {length} bytes"); // still usable — we only lent it

    let moved = greeting;                    // MOVE: ownership transfers
    // println!("{greeting}");               // ERROR: value borrowed after move
    println!("{moved}");                     // the new owner is fine
}                                            // `moved` goes out of scope -> buffer freed

fn measure(text: &str) -> usize {
    text.len()
}                                            // the borrow ends; nothing is freed here
The mental model that helps most

Think of a value as a physical object rather than a name. You can give it away (a move), let people look at it (any number of &T), or hand it to exactly one person to modify (&mut T). What you cannot do is give it away and keep using it, or let someone edit it while others are reading. Stated that way, every borrow-checker error you will meet is obvious in hindsight.

Why Rust is Worth Learning

The learning curve is real, and pretending otherwise does nobody any favours. What you pay in upfront effort is returned during maintenance — the phase where software actually spends its life:

  • No undefined behaviour in safe code: dangling pointers, double-frees and null dereferences are ruled out by the type system rather than becoming production incidents. An out-of-bounds index is a clean, predictable panic, not silent memory corruption.
  • Fearless concurrency: the same ownership rules that govern memory also rule out data races. The Send and Sync traits let the compiler reject unsafe sharing between threads, so parallelising a hot loop stops being a source of dread.
  • Zero-cost abstractions: generics, iterators, closures and pattern matching are resolved at compile time through monomorphisation and inlining. Idiomatic, expressive Rust typically compiles to the same machine code you would have written by hand.
  • Errors you cannot ignore: fallible operations return Result<T, E> and optional values return Option<T>. Both are ordinary enums the compiler forces you to handle, which is why Rust has no null and no invisible exceptions.
  • Tooling that ships in the box: toolchain management (rustup), builds, dependencies and tests (cargo), formatting (rustfmt), linting (clippy), documentation (rustdoc) and a first-class language server (rust-analyzer) are all official and all consistent across projects.
  • A compiler that teaches: Rust's error messages name the rule you broke, point at both ends of the conflict, and frequently print the exact edit that fixes it.
Where Rust is not the obvious choice

Rust rewards programs that must be fast, correct and long-lived. For a one-off script, a quick data exploration, or a team with no appetite for a new language, a garbage-collected language will often get you there sooner. Knowing when not to reach for a tool is part of knowing the tool.

Getting Started

Install the toolchain, compile a single file to see the compiler work, then switch to Cargo for everything else.

Install with rustup

rustup is the official installer. It manages compiler toolchains, keeps them updated, and lets you add extra compilation targets later — including the WebAssembly target used on the WebAssembly page.

macOS / Linux — run this in a terminal:

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh

Windows — download and run the installer from rustup.rs. It will also prompt you to install the Microsoft C++ build tools, which Rust uses as its linker.

Then confirm the install and keep it current:

# Should print something like: rustc 1.98.0 (1159e78c4 2026-08-20)
rustc --version
cargo --version

# Update every installed toolchain and component
rustup update
Add the editor experience

Install the rust-analyzer extension for VS Code (or the Rust plugin for a JetBrains IDE). Inline type hints and instant error underlining shorten the ownership learning curve more than anything else on this page.

Compile a single file with rustc

For a first experiment, invoke the compiler directly. You will not do this often — but it is worth seeing once, so that Cargo feels like a convenience rather than magic.

1. Create hello.rs:

fn main() {
    // The exclamation mark means `println` is a macro, not a function.
    // Macros are expanded at compile time — this one type-checks
    // your format string against its arguments.
    println!("Hello, world!");

    let name = "Ferris";
    println!("Hello, {name}!"); // inline captured identifier
}

2. Compile it:

rustc hello.rs

3. Run the binary it produced:

# macOS / Linux
./hello

# Windows
.\hello.exe

That binary is self-contained: it needs no interpreter and no runtime installed on the target machine.

Use Cargo for everything else

Cargo is Rust's build system, dependency manager, test runner and documentation generator in one command. Real projects always use it. 

# Create a new binary project (use --lib for a library)
cargo new hello_project
cd hello_project

# Compile and run in one step
cargo run

# Type-check without producing a binary — much faster, use it constantly
cargo check

# Run the test suite (including examples in your doc comments)
cargo test

# Format the whole project to the community standard
cargo fmt

# Lint for common mistakes and unidiomatic code
cargo clippy

# Build an optimised binary into target/release/
cargo build --release

# Add a dependency (edits Cargo.toml for you)
cargo add serde --features derive
Always benchmark the release build

The default cargo run uses the debug profile: no optimisation, plus integer-overflow checks and full debug symbols. Debug builds can be ten to fifty times slower than release builds. If Rust ever seems slow, check which profile you measured before drawing conclusions.

What Cargo generated

cargo new creates a small, conventional tree. Cargo finds these paths by convention, so there is nothing to configure:

hello_project/
├── Cargo.toml      # name, version, edition, dependencies
├── Cargo.lock      # exact resolved versions (commit this for binaries)
├── .gitignore
└── src/
    └── main.rs     # binary crate root — `fn main()` lives here
                    # (a library crate uses src/lib.rs instead)

And the manifest itself:

[package]
name = "hello_project"
version = "0.1.0"
edition = "2024"

[dependencies]
# Crates from crates.io go here, e.g.
# serde = { version = "1", features = ["derive"] }
Term What it means
Crate The unit of compilation — one library or one binary.
Package What a Cargo.toml describes: up to one library crate plus any number of binaries.
Module A namespace inside a crate, declared with mod. Items are private unless marked pub.
Workspace Several packages sharing one Cargo.lock and one target/ directory.

Learning to Read the Compiler

Rust's compiler is the best teacher you will have, but only if you slow down and read what it says. A typical borrow error looks like this: 

error[E0502]: cannot borrow `scores` as mutable because it is also borrowed as immutable
  --> src/main.rs:5:5
   |
4  |     let first = &scores[0];
   |                  ------ immutable borrow occurs here
5  |     scores.push(42);
   |     ^^^^^^^^^^^^^^^ mutable borrow occurs here
6  |     println!("{first}");
   |               ------- immutable borrow later used here

Read it in four moves, and it stops being intimidating:

  1. The rule. The headline names exactly which rule was broken — here, shared and mutable borrows cannot overlap.
  2. The two ends. Rust shows you both conflicting lines, not just the one that failed. Line 4 opened the borrow, line 5 collided with it.
  3. The lifetime. The last note is the important one: the borrow lives until line 6, because that is where it is last used. Move that use earlier — or clone the value — and the conflict disappears.
  4. The full explanation. Every code has a long-form write-up with worked examples. Run rustc --explain E0502 to read it in your terminal.
Let the machine do the boring half

Many diagnostics come with a machine-applicable fix. cargo fix applies those automatically, and cargo clippy --fix does the same for lint suggestions. Both refuse to run on a dirty working tree by default, so your changes stay reviewable.

A Practical Learning Path

Rust is best learned in layers. Trying to understand lifetimes on day one is the most common way people bounce off the language. This order works:

  1. Syntax and control flow. Variables, functions, if, loops and match. Enough to solve small exercises. → Control Flow
  2. Ownership, borrowing and lifetimes. Fight the borrow checker deliberately. Write code that fails, read the error, fix it. This is the investment that pays for everything after.
  3. Collections and iterators. Vec, HashMap, slices, and the iterator adapters that replace most hand-written loops. → Collections & Iterators
  4. Error handling. Option, Result, the ? operator, and when to reach for anyhow (applications) versus thiserror (libraries).
  5. Traits and generics. Write your own trait, implement it for two types, then accept impl Trait as a parameter. Generic code stops feeling abstract very quickly.
  6. Doing real work. Read and write files, parse text and JSON, talk to a database, call an HTTP API. → Files & I/O, JSON & Text, Databases & CSV, HTTP
  7. Async and concurrency. Threads and channels first, then async/await with Tokio. Learning them in that order avoids a lot of confusion.
